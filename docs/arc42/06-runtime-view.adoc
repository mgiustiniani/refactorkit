== Runtime Scenario: Safe Java Refactoring through CLI

[cols="1,3",options="header"]
|===
|Step |Interaction

|1
|Developer runs a CLI command such as `rename`, `move-class`, `organize-imports`, `safe-delete`, `extract-method`, or `change-signature`.

|2
|CLI scans or loads the target workspace and builds a `ProjectSnapshot`.

|3
|CLI delegates Java-specific analysis to `JavaLanguageAdapter` / planner classes.

|4
|For an admitted managed or refused result, the planner returns a `PatchPlan` with affected files, workspace edits, diagnostics, warnings, confidence, risk level, and an explicit JDT-backed, structural, or refusal classification. The bounded Java/Maven CLI `moveClass` path instead starts at the operation-specific `JavaMoveClassOperationDispatcher`. Its `Plan(JavaMoveClassPreview)` arm may carry managed, refused, or result-owned typed structural-refusal results and rejects lexical evidence; `Guidance(JavaMoveClassReviewOnlyGuidance)` carries REQ-003 plus four bounded REQ-008 preview uncertainties; and `LexicalReview(JavaMoveClassLexicalFallbackReviewEnvelope)` carries REQ-004 alone. A legacy lexical compatibility preview is projected to `LEXICAL_FALLBACK_REVIEW` before generic patch rendering.

|5
|User reviews the preview. If applying, `PatchEngine` acquires the workspace writer lock, checks the derived current snapshot hash, revalidates affected paths, probes durability capability, renders complete post-images, durably journals intent, stages same-directory files, and commits per-path atomic replacements/deletes with directory flushes.

|6
|Only after every write succeeds does the current flow return compensating rollback edits; the CLI then persists transaction metadata. A write or process failure can therefore leave partial state without a durable recovery record.

|7
|Normal rollback compares every affected path with the exact retained post-image under the workspace lock and refuses `rollback.conflict` without writes. Explicit force restores pre-images and records the override. Production managed Java apply uses a central staged JDT diagnostics gate; complete metadata restoration remains planned.
|===

Status: implementation-informed from CLI, Java adapter, patch engine, testkit docs, and `docs/transactionality-audit.md`. This is a preflighted compensatable batch, not an ACID or crash-safe transaction.

== Runtime Scenario: Behavior-preserving Pending-plan Retention

Status: implementation-informed for the bounded source-built/in-process runtime. `modules/refactorkit-core/src/main/kotlin/org/refactorkit/core/PendingPlanStore.kt` is used by the exact production session paths `modules/refactorkit-daemon/src/main/kotlin/org/refactorkit/daemon/DaemonSession.kt`, `modules/refactorkit-lsp/src/main/kotlin/org/refactorkit/lsp/LspSession.kt`, and `modules/refactorkit-mcp/src/main/kotlin/org/refactorkit/mcp/McpSession.kt`. Implemented-and-validated REQ-PENDING-PLAN-STORE-001/002 exercise the matrix below without changing protocol or authority behavior.

[cols="1,3",options="header"]
|===
|Step |Interaction

|1
|The daemon, LSP, or MCP surface performs its existing preview and admission checks. Only after that surface-owned decision does it insert the exact plan plus any surface-owned apply-critical metadata into its own instance of the shared generic core store. The MCP external-import path deliberately retains its current unconditional insertion exception in this behavior-preserving slice.

|2
|Insertion retains the exact payload under the plan identity. The store is in-memory and per session; it does not regenerate a plan and does not share entries between sessions or surfaces.

|3
|A successful lookup returns the exact payload and mutates access recency. At most 128 entries remain. Inserting a 129th entry silently removes the least-recently accessed entry; touching the oldest before that insertion makes the previously second-oldest entry the eviction candidate.

|4
|The surface performs its existing language/lease, snapshot, diagnostics, approval, and `PatchEngine` work. The plan ID is only a revocable lookup handle: explicit apply invocation remains the approval event, and all normal managed-write gates still apply.

|5
|After apply, refusal, rollback, project/document lifecycle, or close, the surface invokes remove or clear according to its existing policy below. The shared store does not infer snapshot changes and does not run lifecycle callbacks.

|6
|Eviction, discard, selected removal, and clear remove references only. They create no filesystem write, `.refactorkit` state, workspace lock, WAL record, transaction, rollback evidence, or protocol notification.
|===

Qualification is limited to dated mutable source-built/in-process and aggregate whole-working-tree evidence plus inspected surface adoption; it does not cover packaged or cross-platform execution, concurrent rollback, crash/restart, general rollback authority, numerical coverage, or altered `PatchEngine` authority.

[cols="1,3",options="header"]
|===
|Step |Implementation-informed interaction

|1
|The surface completes its existing prerequisites, resolves the workspace root, selects `RollbackMode`, and passes the supplied raw transaction-ID string, its chosen `RollbackLookupVisibility`, and a surface-owned preflight guard to the language-neutral core executor. CLI/LSP/MCP select `APPLIED_ONLY`; daemon selects `JOURNAL_RECORD`. Mode selection remains outside the executor.

|2
|`ManagedRollbackExecutor` calls `TransactionId.parseOrNull` on the raw string exactly, without trimming, case-folding, or canonicalization. Invalid input returns typed `InvalidTransactionId` before journal access, guard invocation, workspace-lock creation/acquisition, or engine invocation.

|3
|For a parsed ID, the executor performs exactly one pre-lock `TransactionLog.loadRecord` against the same normalized workspace journal used by `PatchEngine`. Absence returns `TransactionNotFound`; a thrown `TransactionLogException` returns `JournalLookupFailed` with its exact code, message, and cause. It does not call `load` and then reload the full record.

|4
|The executor applies visibility to that one result. `APPLIED_ONLY` exposes only a record whose state is `APPLIED`; every other state is observationally not found and short-circuits before guard/engine work. `JOURNAL_RECORD` exposes any decodable, ID-matching state so daemon behavior continues to let `PatchEngine` perform authoritative under-lock recovery/state handling.

|5
|Only after visible resolution, the executor invokes the generic read-only guard with the exact resolved record. CLI, daemon, and MCP allow. LSP first rejects if any open document is dirty versus disk and otherwise rejects if an affected rollback path is open, using `resolvedRecord.transaction.rollbackEdit.affectedFiles()`. Rejection returns `PreflightRejected` with that record and the unchanged surface-owned rejection; no engine call occurs.

|6
|After an allow decision, the executor invokes public `PatchEngine.rollback(resolvedRecord.transaction, suppliedMode)` exactly once. `PatchEngine` then acquires its workspace lock, performs interrupted-lifecycle handling, reloads the journal under lock, and retains all APPLIED-state, recovery, image, conflict, force, metadata-restoration, and journal-transition authority. The executor does not duplicate those rules.

|7
|The exact engine `ApplyResult.Applied` transaction is wrapped with the same resolved pre-lock record as `RolledBack`. For `ApplyResult.Refused`, diagnostic order and values are copied into a detached unmodifiable snapshot before return; mutating the source list afterward cannot alter the outcome. A `TransactionLogException` escaping the one rollback call becomes distinct `RollbackCallJournalFailed` with that same record and exact exception identity. Arbitrary guard/engine exceptions are not relabeled as journal failures. The outer record is lookup evidence, not current or post-rollback state.

|8
|After the typed outcome returns, each surface preserves its existing rendering and completion behavior: daemon may derive inverse `changedFiles` from the retained record's `forwardEdit`, refresh snapshot/index, run diagnostics, and clear pending/audit state; LSP/MCP/CLI keep their own response, refresh, publication, and lifecycle rules. No post-call record reload is introduced for projection.
|===

Delegated `c4model` validation of `docs/c4/workspace.dsl` passed with no model change. == Runtime Scenario: Cross-surface Legacy Lexical-fallback Review

Status: implementation-informed for implemented-and-validated REQ-JAVA-MAVEN-MOVE-AUTH-004. The evidence exercises one source-built/in-process production scenario through `JavaMoveClassOperationDispatcher`, `RefactorKitCli`, `RecipeEngine`, `DaemonSession`, `LspSession`, and `McpSession`; it does not qualify packaged processes, stdio/editor transport deployments, runtime distributions, native platforms, or general move-class authority.

[cols="1,3",options="header"]
|===
|Step |Interaction

|1
|The direct Java move-class operation API (`JavaMoveClassOperationDispatcher.preview`), CLI, recipe, daemon JSON-RPC session, managed LSP command session, or MCP tool session submits the same normalized Maven `moveClass` request against an exact `ProjectSnapshot`. This direct path is the Java operation outcome dispatcher, not the generic `LanguageAdapter` `PatchPlan` API.

|2
|Operation-specific Java analysis cannot establish semantic authority and creates a legacy internal compatibility preview with `LEXICAL_FALLBACK`. `JavaMoveClassOperationDispatcher` immediately projects that preview to its `LexicalReview` outcome. The compatibility plan's UUID `PlanId`, workspace edit, ranges, and replacement/create bytes remain internal and never cross the outcome/protocol boundary.

|3
|Before generic rendering, pending-plan registration, recipe reduction, or LSP `WorkspaceEdit` conversion, the dispatcher builds canonical schema-v1 `LEXICAL_FALLBACK_REVIEW`. Canonical JSON hashing produces `requestSha256`, exact `snapshotSha256`, hidden `reviewArtifactSha256`, and sorted-fact `evidenceSha256`. The hidden review-artifact identity commits to normalized internal compatibility file operations, exact edit ranges, and replacement/create byte hashes; exposed residual records do not contain those details. The deterministic non-capability `operationId` is `lexical-review-<sha256>` over the four identities and fixed disposition.

|4
|The surface returns the same immutable envelope with `semanticCompleteness=NOT_SEMANTICALLY_PROVEN`, `authorityStatus=REVIEW_ONLY`, `evidenceKind=LEXICAL_FALLBACK`, `managedWriteEligibility=INELIGIBLE`, and `blockerCode=evidence.insufficient`. Residual guidance contains only normalized path, current content SHA-256, typed risk facts, and `managedEdit=false`; it is capped at 200 records/262,144 canonical record bytes, reports `recordCompleteness=COMPLETE or TRUNCATED`, deterministic returned-category counts, and the four fixed next actions. The envelope has no protocol plan/edit/range/replacement/apply token, `changes`, `documentChanges`, transaction, or rollback field. Promotion metadata and internal random plan IDs do not affect any identity.

|5
|The Java-owned audit cache stores exact immutable envelopes only in an in-memory LRU keyed by `operationId`, bounded to 128 entries and 16,777,216 canonical bytes. Daemon/LSP/MCP session dispatchers insert no pending plan and clear audit state on relevant project, snapshot, mutation, semantic-session, initialization, and close transitions. CLI and recipes use short-lived dispatchers. A recipe stops immediately, discards prior staged images, returns a null aggregate plan, and creates no transaction.

|6
|Daemon, LSP, and MCP use the shared `RefactoringApplyIdentity.parse`, which requires exactly one non-blank `operationId` or `planId`. A still-known operation returns the same envelope and typed `evidence.insufficient` before `PatchEngine`, workspace lock, WAL, editor application, or mutation. Daemon and LSP use `PLAN_VALIDATION_FAILED (-32008)` and preserve blocker/envelope JSON-RPC error `data`; MCP returns `isError=true` with equivalent `structuredContent`.

|7
|No identity, both identities, a blank/non-string identity, an unknown or evicted `operationId`, and an arbitrary/unknown `planId` including `plan-lexical` are `INVALID_PARAMS (-32602)`. Unknown identity never becomes typed known lexical evidence.

|8
|The core lexical evidence gate remains defense in depth for direct compatibility-plan apply and refuses before lock/WAL. A fresh full-reactor scan with complete exact bindings preserves the existing `Plan` outcome with `SEMANTIC_PREVIEW`, `JDT_BINDING`, `ELIGIBLE`, and its managed edit; neither the old compatibility plan nor the lexical envelope is promoted.
|===
