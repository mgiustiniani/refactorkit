== Runtime Scenario: Safe Java Refactoring through CLI

[cols="1,3",options="header"]
|===
|Step |Interaction

|1
|Developer runs a CLI command such as `rename`, `move-class`, `organize-imports`, `safe-delete`, `extract-method`, or `change-signature`.

|2
|CLI scans or loads the target workspace and builds a `ProjectSnapshot`.

|3
|CLI delegates Java-specific analysis to `JavaLanguageAdapter` / planner classes.

|4
|For a managed or refused result, the planner returns a `PatchPlan` with affected files, workspace edits, diagnostics, warnings, confidence, risk level, and an explicit JDT-backed, lexical, or refusal classification. The bounded Java/Maven CLI `moveClass` path first uses `JavaMoveClassOperationDispatcher`: its `Plan` arm wraps the existing `JavaMoveClassPreview`, while its disjoint `Guidance` arm carries only `JavaMoveClassReviewOnlyGuidance`.

|5
|User reviews the preview. If applying, `PatchEngine` acquires the workspace writer lock, checks the derived current snapshot hash, revalidates affected paths, probes durability capability, renders complete post-images, durably journals intent, stages same-directory files, and commits per-path atomic replacements/deletes with directory flushes.

|6
|Only after every write succeeds does the current flow return compensating rollback edits; the CLI then persists transaction metadata. A write or process failure can therefore leave partial state without a durable recovery record.

|7
|Normal rollback compares every affected path with the exact retained post-image under the workspace lock and refuses `rollback.conflict` without writes. Explicit force restores pre-images and records the override. Production managed Java apply uses a central staged JDT diagnostics gate; complete metadata restoration remains planned.
|===

Status: implementation-informed from CLI, Java adapter, patch engine, testkit docs, and `docs/transactionality-audit.md`. This is a preflighted compensatable batch, not an ACID or crash-safe transaction.

== Runtime Scenario: AI-assisted Refactoring through MCP

[cols="1,3",options="header"]
|===
|Step |Interaction

|1
|Local LLM agent calls `project_scan` for a workspace root.

|2
|Agent asks for `project_summary`, symbol resources, definitions, references, diagnostics, or `generate_context_bundle`.

|3
|Agent calls `preview_refactoring` or `import_external_java_class` instead of editing files directly.

|4
|MCP server delegates to core, Java adapter, and/or web importer to produce a preview.

|5
|Agent/user inspects affected files, warnings, and diagnostics.

|6
|Agent explicitly calls `apply_refactoring`; the current engine treats this invocation as sufficient even though `requiresUserApproval` is advisory metadata rather than a separately enforced approval state.

|7
|Before mutation, `PatchEngine` persists `PREPARED`/`APPLYING` journal intent. After success, compensation is available through `rollback_refactoring`; lifecycle history is retained. Normal rollback is still not conflict-safe against later workspace edits.
|===

Status: implementation-informed from `docs/ai-workflow.md`, `docs/integration-contracts.md`, and the transactionality audit; stable MCP status remains capability-by-capability and acceptance-gated. MCP managed apply is a compensatable batch, not a durable transaction.

== Runtime Scenario: Editor Operation through LSP

[cols="1,3",options="header"]
|===
|Step |Interaction

|1
|External editor starts `refactorkit-lsp` over stdio.

|2
|Editor sends LSP requests such as definition, references, prepareRename, rename, codeAction, documentSymbol, semanticTokens, or diagnostics.

|3
|LSP server maps requests to Java/core model operations.

|4
|For native rename and WorkspaceEdit-returning commands, the server labels the result client-managed/no-rollback; the editor applies it outside `PatchEngine`. Open-buffer text edits carry the exact tracked document version.

|5
|`didOpen`/full-sync `didChange` overlays feed planning. Non-increasing versions and incapable clients for structural/open-document edits are refused; managed disk apply/rollback rejects unsaved or affected-open documents (`TX-007` closed).

|6
|For the custom `refactorkit.applyPlan` command, RefactorKit owns sequential writes and post-apply compensation logging, with the same non-crash-safe limitations as other managed apply paths.
|===

Status: implementation-informed from `docs/integration-contracts.md` and `docs/transactionality-audit.md`; stable LSP status remains capability-by-capability and acceptance-gated. Native edits and RefactorKit-managed apply have distinct transaction boundaries.

== Runtime Scenario: Daemon Capability Discovery Before Project Open

[cols="1,3",options="header"]
|===
|Step |Interaction

|1
|A daemon client starts the local daemon over stdio and sends JSON-RPC method `server.capabilities` before `project.open`.

|2
|The daemon returns RefactorKit name, version, API version, protocol `json-rpc-2.0`, and transport `stdio` without creating a project session or accessing a workspace. The stable target value is API version `1.0`; the current baseline remains pre-stable until contract acceptance.

|3
|The response lists documented daemon methods with stability, `requiresProject`, and `writesWorkspace` descriptors. `java.importExternalClass` is explicitly classified as experimental.

|4
|The response also advertises preview-before-apply, snapshot validation, transaction rollback, and workspace-scoped-write safety flags.

|5
|The client uses the metadata to select compatible calls and still opens a project before invoking methods whose descriptor requires one. Discovery itself grants no filesystem access.
|===

Status: implementation-informed from `DaemonSession`, its daemon contract test, `docs/integration-contracts.md`, and the transactionality audit. Successful apply/rollback rescans into the stored session, clears stale pending plans, returns the new snapshot hash, and makes subsequent summary/symbol queries current (`TX-018` closed).

== Runtime Scenario: Staged Recipe Apply

[cols="1,3",options="header"]
|===
|Step |Interaction

|1
|The recipe engine scans one initial snapshot and previews the first step without writing files.

|2
|`WorkspaceEditSimulator` applies the step to an immutable staged snapshot using the same structural-segment normalization as `PatchEngine`; each later step plans against that evolving snapshot.

|3
|Any refusal, diagnostics error, invalid edit, or later planning failure returns before journaling and leaves the workspace untouched.

|4
|After all steps succeed, the engine computes one initial-to-final workspace delta and exposes one recipe-wide preview plan.

|5
|Apply validates the initial engine-owned snapshot and commits the recipe-wide plan through one lock/WAL/staged replacement transaction. No-op recipes create no transaction.
|===

Status: implementation-informed from `docs/transactionality-audit.md`; `TX-008` is closed with one staged recipe transaction.

== Runtime Scenario: External Java Class Import Preview

[cols="1,3",options="header"]
|===
|Step |Interaction

|1
|User or agent provides Java source from clipboard, file, URL, snippet, or LLM response.

|2
|Importer strips Markdown fences and records provenance/license warnings.

|3
|Importer validates target package, detects top-level public types, splits multiple public types when needed, rewrites package declaration, and organizes imports.

|4
|Importer checks naming conflicts in the scanned snapshot or filesystem.

|5
|Importer returns a preview-only `PatchPlan`; apply is delegated to the patch engine after user approval.
|===

Status: implementation-informed from `docs/external-class-importer.md`.

== Runtime Scenario: Authoritative Module-targeted Maven Diagnostics

Status: confirmed architecture; active, product-critical. The first release-8/current-release packaged and post-model module-filter rows are implemented; this scenario does not claim completion of `RPK-JAVA-DIAG-001..007`.

[cols="1,3",options="header"]
|===
|Step |Interaction

|1
|The caller opens the declared full Maven reactor root. RefactorKit treats that root as workspace and effective-model authority and performs no implicit upward, sibling, or outward discovery.

|2
|The Build Model provider constructs the active full reactor and independent main/test source-set environments from non-executable evidence. Only safely declared, already materialized generated sources are included; Maven, wrappers, lifecycle goals, plugins, annotation processors, credential helpers, and settings credentials do not execute.

|3
|For each affected source set, the Java adapter selects the exact immutable, hash-attested Java platform signatures for effective `--release R`. A no-release/source-only configuration requires an explicitly qualified JDK platform. Missing or unqualified platform evidence makes only the dependent source-set closure typed unavailable.

|4
|A module-targeted request computes the selected module's Maven dependency and dependent-impact closures over the already constructed full-reactor model. The module selector filters returned rows; it does not redefine the workspace or model.

|5
|If any required affected environment is unavailable, RefactorKit returns concise typed source-set roots, preserves genuine syntax findings, suppresses only derivative binding cascades, and grants no semantic mutation authority. Named JPMS/module-path reactors return typed unsupported until their dedicated slice is accepted.

|6
|If the environment is complete, JDT produces RefactorKit diagnostics bound to snapshot, overlay/disk mode, source-set closure, model/classpath evidence, platform-signature identity, and provider identity. Maven compile/test may be reported separately but cannot suppress or excuse these diagnostics.

|7
|Managed preview/apply compares baseline and exact staged post-image diagnostics across the affected and dependent-impact closure. Default policy rejects introduced errors; strict mode requires zero staged errors. Any affected-environment unavailability blocks regardless of baseline, and post-apply/rollback results bind the committed/restored snapshots.
|===

== Runtime Scenario: Review-only Java/Maven Move Guidance

Status: implementation-informed for the four bounded REQ-JAVA-MAVEN-MOVE-AUTH-003 defects through the Java dispatcher and source-built CLI. This is not a generic cross-surface result algebra. Force/recipe/daemon/managed-LSP/MCP parity remains acceptance scope of absent REQ-JAVA-MAVEN-MOVE-AUTH-004; structural-loss and post-preview drift refusals remain scope of absent REQ-JAVA-MAVEN-MOVE-AUTH-008.

[cols="1,3",options="header"]
|===
|Step |Interaction

|1
|The CLI scans with the ordinary `JavaProjectScanner`, then submits an otherwise supported same-module/source-set Maven `moveClass` request. `JavaMoveClassOperationDispatcher` and `JavaMoveClassPlanner` share the same side-effect-free, plan-free `JavaMoveClassRequestValidator` preflight for package, symbol, generated-source, and destination checks.

|2
|After supported preflight, bounded evidence collection detects one safely enumerable authority defect: a readable source omitted from the scanner inventory, an expected/observed system-path artifact fingerprint mismatch, a recovered target-use binding, or an expected/observed materialized-generated-root inventory fingerprint mismatch. The source omission comes from an effective primary Maven `testSourceDirectory` replacement, modeled separately from additive build-helper/Kotlin roots; additive declarations retain the default Java root, and the scanner interprets configuration without executing a plugin. Strict format-version-1 expected-source and generated-root manifests are already bound into the snapshot as auxiliary files; the classpath case binds its strict manifest content hash and expected/observed artifact fingerprints. The generated root belongs to `catalog-generated-support:main`.

|3
|The Java adapter constructs a fresh immutable `JavaMoveClassReviewOnlyGuidance` (`resultType=REVIEW_ONLY_GUIDANCE`) bound to request identity, snapshot SHA-256, and canonical evidence SHA-256. Schema version 1 emits typed module/source-set blockers, separately typed candidate/residual groups, explicit completeness and the bounded source-inventory omission, and ordered authority-restoration actions. Checklist version 1 emits the fixed seven human/VCS-owned steps. The value has no `PatchPlan`, `PlanId`, `WorkspaceEdit`, replacement text, transaction identity, rollback capability, or plan conversion and enters no pending-plan store. The CLI renders the same data as JSON.

|4
|The user may inspect the guidance or restore inputs outside RefactorKit. Generated sources are restored or rematerialized by the owner outside RefactorKit; no generator execution is implied. Manual edits use VCS checkpoint/revert rather than RefactorKit rollback.

|5
|If the same CLI command includes `--apply`, `RefactorKitCli.cmdMoveClass` recognizes the guidance arm, writes `guidance.nonManaged`, and returns failure before `applyPlanAndLog`. `PatchEngine.apply` is therefore not invoked; no `.refactorkit`, workspace lock, WAL, pending plan, or transaction is created, and bytes, paths, inventories, and snapshot hash remain unchanged.

|6
|After restoration, a full reactor rescan and a new preview may independently produce a new `SEMANTIC_PREVIEW`. The guidance object itself is never promoted or converted into a plan, and later Maven/manual success does not retroactively change its evidence classification.

|7
|The validated four cases keep every required input readable, safely contained, and bounded. Lost/unreadable/unsafe/unbounded structural inputs and changes after request/snapshot/evidence binding are deliberately excluded; their fail-closed behavior remains unvalidated REQ-JAVA-MAVEN-MOVE-AUTH-008 scope rather than an inference from this guidance flow.
|===
