== Level 1: RefactorKit System

RefactorKit provides deterministic code-intelligence and refactoring capabilities with preview, validation, managed apply, and compensation semantics. Managed apply is a WAL-backed, recoverable, staged per-path transaction rather than one filesystem-wide ACID commit; admitted native LSP edits are version-checked and explicitly client-managed/no-rollback, and recipes reduce eligible staged steps to one managed transaction. Implemented REQ-JAVA-MAVEN-MOVE-AUTH-004 adds an operation-admission invariant for Java/Maven `moveClass`: legacy lexical fallback is an edit-free protocol review envelope, not a managed plan, client edit, or recipe aggregate. RefactorKit exposes capabilities through CLI, daemon, LSP, MCP, and library integration modes. For `v1.0.0`, the core patch, documented CLI, and documented daemon surfaces become stable API `1.0` contracts only after acceptance; LSP and MCP surfaces are stable only capability by capability where explicitly classified.

Status: implementation-informed for the bounded source-built/in-process extraction. * identity-keyed insertion and exact payload retention;

* side-effect-free removal and clear; and

The implemented language-neutral core application service owns one narrow sequence:

* parse the supplied raw string exactly through `TransactionId.parseOrNull`;
* call `TransactionLog.loadRecord` exactly once before the engine lock and apply caller-selected `RollbackLookupVisibility`;
* return not-found before guard/engine work when no record is visible;
* pass the exact visible `TransactionJournalRecord` to a generic surface-supplied preflight guard;
* after an allow decision, call public `PatchEngine.rollback(record.transaction, suppliedMode)` exactly once; and
* return a typed outcome that retains the exact resolved pre-lock record for every post-resolution branch.

`APPLIED_ONLY` is selected by CLI, LSP, and MCP; it exposes only `JournalState.APPLIED`. `JOURNAL_RECORD` is selected by daemon; it exposes every decodable, ID-matching journal state and leaves state/recovery refusal to `PatchEngine`. The LSP supplies the only nontrivial current guard, preserving its dirty-document-first and affected-open-document-second checks from `record.transaction.rollbackEdit.affectedFiles()`; CLI, daemon, and MCP supply allow-all guards. The guard is deliberately pre-lock and does not replace authoritative under-lock validation.

The outcome algebra distinguishes invalid ID, visible-record absence, journal lookup failure, preflight rejection, journal failure during the rollback call, exact engine-applied success, and engine refusal. Lookup failure has no resolved record; every branch after successful resolution carries the same full record, including `forwardEdit`, so daemon inverse-change projection needs no second lookup. Journal failures preserve exact exception identity. A refusal preserves diagnostic order and values in a detached unmodifiable snapshot, so later mutation of the source list cannot change the outcome. The record is named *resolved*, not current or post-rollback: `PatchEngine` deliberately reloads journal state under its workspace lock and may durably advance it after the outer lookup.

This component has no language-adapter dependency and owns no renderer, protocol code, mode choice, diagnostics, refresh/index/session lifecycle, pending-plan/audit clearing, authorization, direct write, WAL/recovery replacement, journal redesign, or rollback algorithm. It is internal C3-scale orchestration within the existing Core Patch and Model Engine and existing integration-to-core dependencies. No actor, container, store, deployment node, or relationship changed. Delegated `c4model` review validated `docs/c4/workspace.dsl` and confirmed that no C4 update is required. This evidence does not qualify packaged or cross-platform execution, concurrent rollback, crash/restart behavior, numerical coverage, or any alteration of `PatchEngine` rollback authority.
