== Patch Safety

All mutating operations are represented as `PatchPlan`s containing operation name, status, snapshot hash, confidence, required approval flag, summary, affected files, `WorkspaceEdit`, diagnostics, warnings, and risk level.

`PatchEngine` validates that:

* only preview plans can be applied;
* current snapshot hash matches the preview hash;
* edit paths stay inside the workspace root, retaining the `path.outsideWorkspace` diagnostic;
* every symbolic-link path component below the workspace root is refused with `path.symbolicLink`, conservatively even when the link resolves inside the workspace;
* text edits do not overlap; and
* ordered create, modify, rename, and delete operations have valid file existence/type transitions.

The ordered state simulation runs before the first write. It prevents a predictable later missing-file or existing-file refusal from leaving an earlier edit applied, while still allowing valid sequences such as modify then rename. Tests cover an outside-pointing symlink with no write, create followed by a missing-file delete with no partial create, and a successful modify-then-rename sequence.

Status: implementation-informed for structural/overlap validation, conservative symlink refusal, ordered state simulation, and snapshot-aware managed-write isolation. Eligible managed paths hold a non-blocking OS workspace lock across validation/apply/rollback and revalidate initially affected paths under that lock for first-party managed integrations; immutable ineligible evidence can refuse before lock acquisition. The hash-only overload is removed, all callers use the snapshot-aware contract, and snapshot hashes bind declared source scope that the engine independently walks/rehashes under lock. Classpath evidence covers active entries, prospective compiled outputs, local JAR directories, and generated declarations; all are recomputed before journaling (`TX-005` and source/classpath-scope `TX-014` closed). Modify entries are normalized into one original-content coordinate space per path/structural segment, with merged overlap checks, complete preflight rendering, and line/character-within-line validation (`TX-009`, `TX-010` closed). Full post-images are rendered before mutation, staged in same-directory temporary files, forced, atomically replaced, and followed by directory force; unsupported durability capability is reported/refused (`TX-001`, `TX-006` implementation-closed on supported filesystems). Managed flows provide filesystem-qualified WAL recovery with per-path atomic commits; they do not claim an impossible filesystem-wide atomic rename across independent paths. No RefactorKit-managed production write may bypass `PatchEngine`; native LSP client writes are outside this boundary.

== Compensation, Journal, and Recovery

Before every managed write, `PatchEngine` durably creates a versioned `PREPARED` journal record containing transaction identity, operation, forward/compensation edits, and affected-path pre/post images, then advances to `APPLYING`. Apply, rollback, and explicit restart recovery retain lifecycle states through `APPLIED`, `ROLLING_BACK`, `ROLLED_BACK`, or `RECOVERY_REQUIRED`; integrations no longer persist metadata after mutation (`TX-002` closed, `TX-001` narrowed). Read-only daemon/MCP/LSP startup calls `inspectRecovery`, which performs no lock-file, directory, quarantine or journal write and refuses incomplete state until `patch.recover` is explicitly authorized.

Transaction identifiers now enforce the generated UUIDv4 grammar; normalized transaction-log paths are contained, reject symbolic links and non-regular records, apply owner-only permissions where supported, and report coded corruption/path failures (`TX-003` closed after the audit baseline). Records now retain a versioned lifecycle, forward/compensation edits, pre/post images, failure detail, and atomically/durably replaced history. Schema-v2 canonical SHA-256 checksums, v1-on-update migration, and blocking owner-only corruption quarantine are implemented; schema-v3 adds checksummed implementation/API versions, pre/post scope hashes, and append-only validation/lifecycle/recovery events; v2 checksum verification remains backward compatible; schema-v8 adds independently verified per-image content hashes; TX-011/TX-012 are closed for the reported durability contract. Schema-v8 compensation restores text, POSIX permissions, timestamps, owner/group identity, user-defined attributes, and exposed platform ACLs and removes transaction-created parents deepest-first; external directory contents trigger conflict refusal. The v1 text contract is strict UTF-8 with exact BOM preservation and malformed-input refusal before WAL creation. Standalone directory operations are outside the stable v1 contract (`TX-013` closed by precise scope narrowing).

Normal rollback verifies exact retained post-images under the workspace lock and refuses conflicts without writes; explicit force restores pre-images and records the override (`TX-004` closed for versioned records). Snapshot-aware apply independently rescans hash-bound source roots/extensions/ignore policy under the workspace lock, so stale library snapshots cannot omit newly appeared declared-scope sources. Java classpath artifacts and discovery manifests are likewise fingerprinted and revalidated (`TX-014` closed for source/classpath scope). Recipe steps are evaluated against one evolving immutable snapshot and reduced to one recipe-wide `PatchPlan`; apply creates one WAL transaction, while planning failure writes nothing (`TX-008` closed).

Write-ahead lifecycle, compatible startup compensation, explicit `RECOVERY_REQUIRED`, conflict-safe rollback, durable supported-filesystem replacement, and engine-owned source/classpath scope are implemented. == Diagnostics Model

Diagnostics use structured severity (`INFO`, `WARNING`, `ERROR`), optional source location, optional code, evidence/category, and explicit location precision (`EXACT_RANGE`, `LINE_ONLY`, `NONE`). Java diagnostics currently include duplicate symbol detection, package/path mismatch warnings, and public type/file-name mismatch errors.

Additive API `0.2` `diagnostics.v2` provides the IDE authority envelope for TypeScript/JavaScript: caller request ID, opaque semantic lease, saved and provider snapshot hashes, saved-disk or immutable-editor-overlay authority, exact compiler/toolchain and process attestation, actual compiler limits, structured ready/refused/error state, and bounded diagnostics. Exact ranges are zero-based UTF-16; line-only/no-location variants cannot be promoted to Monaco ranges by inference. Legacy `diagnostics` remains a bare array for compatibility.

The stable target also compares diagnostics before preview, after preview simulation, after apply, and after rollback where an operation requires those gates. A configured regression beyond the approved plan causes refusal.

Status: implementation-informed for the current generic/JDT diagnostics-only gate. It does not establish the planned full-reactor, release-aware Java/Maven authority described below. Managed Java surfaces supply JDT diagnostics to a core gate that compares `S0` and a simulated staged candidate under lock before WAL, refusing new errors or unavailable diagnostics. That candidate is an exact staged `ProjectSnapshot` only when the edit cannot change hash-bound modules, classpath evidence, or build models; for a model-changing descriptor edit, `WorkspaceEditSimulator` preserves stale `S0` semantic metadata and supplies only exact file candidate `C1`. TypeScript managed gates and IDE diagnostics use the independent `typescript-compiler-exact-v1` path rather than LSP publications. Experimental Kotlin diagnostics use `kotlin-compiler-diagnostics-k2-v1`, an external K2 process over an immutable overlay with snapshot/build/toolchain attestation; compiler XML lacks trustworthy end offsets, so diagnostic locations remain explicitly line-only. The separate `kotlin-compiler-jvm-declarations-k2-v1` read row accepts exact compiler PSI declared-type selections only after successful compilation and matching JVM class-file evidence, producing type IDs from binary identity rather than offsets; an implicit companion selects its `object` keyword because it has no source name identifier. The first function row additionally binds an opaque callable ID to generated JVM owner, method name and descriptor and refuses ambiguous overload/bridge evidence. Neither read backend has mutation authority. Direct library apply still requires an explicit gate; TX-015 remains closed for the legacy diagnostics-only mode and is implementation-informed for the separately selected bounded authoritative mode.

==== Laziness, External Resolution, and Ordering

Calling `select` must invoke zero diagnostics providers. For the exact module-rename row it creates only `DiagnosticsGate.lazyAuthoritative`; reading its ID still constructs neither the Java planner gate nor its provider. On first evaluation, core's private lazy authoritative provider uses `LazyThreadSafetyMode.SYNCHRONIZED` to construct one delegate, requires the factory's gate ID to equal the declared ID, requires an authoritative provider, and reuses it for all evaluations. There is deliberately no evaluation observer; the production selector supplies its own factory, and no caller- or test-supplied factory participates in the production apply. Other built-in closures remain lazy, and no Java adapter diagnostics, Maven rebuild, K2/compiler diagnostics, JDT analysis, ephemeral Java compilation, or external synchronized diagnostics may run at selection.

The external resolver is called exactly once and only for row 8 during selection. Daemon supplies its existing `requireSemanticAdapter(languageId).diagnosticsGate()` behavior, including exact TypeScript/JavaScript validation and daemon-specific exceptions; MCP supplies its existing map lookup and MCP-specific exception wording. Resolver exceptions propagate unchanged. The returned gate—including `typescript-compiler-exact-v1` today—is returned unchanged and opaque to `refactorkit-jvm`. The active adapter lookup therefore happens now, but semantic-scope/completeness/toolchain/project-evidence checks and synchronized diagnostics happen later when `PatchEngine` invokes the returned provider. Deferring lookup would remap a missing-adapter protocol error to `diagnostics.unavailable`; eagerly invoking the provider would violate the lock boundary.

Provider output is also preserved verbatim:

* Exact module rename delegates authoritative S0/C1/S1 evaluation to the retained operation-owned gate; generic Java and Maven-ownership providers are not fallback observers for that apply.
* Maven ownership delegates to the supplied Java adapter when no `maven-pom` auxiliary file exists; otherwise its provider materializes tracked files, rebuilds the Maven model offline, and runs that same adapter. This work remains lazy.
* Ordinary Java returns `javaAdapter.diagnostics` without selector-level transformation.
* Kotlin-only returns `KotlinCompilerDiagnosticsResult.diagnostics` directly, including singleton refused/error diagnostics.
* All three mixed planners return available compiler/K2 diagnostics first and converted JDT diagnostics second; mixed-evidence failure returns one synthesized `ERROR`. The Java-to-Kotlin planner retains its ephemeral annotation-processing-disabled Java compilation before K2/JDT evidence.
* External adapters retain their own gate ID, provider, failure, and ordering semantics.

The selector performs no sorting, deduplication, severity conversion, tagging, bounding, or reversal. Ordering remains observable in refusal messages and response diagnostics even though core regression comparison is multiset-based.

==== PatchEngine Authority and Explicit Exclusions

The authority sequence below remains unchanged for diagnostics-only gates. The implemented exact module-rename branch instead uses the already-qualified model-changing authoritative S0/C1/S1 path; adding its lazy selector route changes neither `PatchEngine` ownership nor any other gate identity:

. The surface validates pending identity and its Kotlin lease/index rules, resolves the root, and scans the saved workspace.
. It selects a lazy gate; only external active-adapter lookup may occur at this point.
. It calls `PatchEngine.apply` with the unchanged plan, current snapshot, authorization surface, and selected gate.
. `PatchEngine` acquires the one-writer lock, performs recovery/preflight/snapshot/approval/authority/precondition checks, and only then invokes the provider on baseline and exact simulated staged snapshots.
. `PatchEngine` subtracts preview-approved regressions, refuses unapproved new `ERROR` identities before WAL, and otherwise owns WAL/mutation.
. The same provider checks the rehydrated post-image. Mismatch or unavailability triggers automatic rollback and then one restored-baseline provider check.
. Only after `PatchEngine` returns may a surface render, refresh, close/reset adapters, or clear state according to its existing behavior.

The selector owns none of the following:

* CLI, managed LSP, recipes, testkit, or direct-library selector adoption; all CLI/LSP/MCP preview routes and public daemon/MCP behavior beyond selection;
* daemon post-success response diagnostics or diagnostics bounding;
* preview planner routing, preview diagnostics, diagnostics queries, context/query resources, or symbol/index routes;
* pending-plan identity, lexical-review refusal, Kotlin lease/index checks, saved-workspace scanning, authorization strings, response/error rendering, or plan cleanup;
* Java/Kotlin/TypeScript toolchain and adapter start, stop, restart, close, cache, index, invalidation, or lease lifecycle;
* `PatchEngine`, diagnostics regression identity, provider invocation, workspace locking, apply, WAL, post-image verification, automatic rollback, explicit rollback, or recovery.

Daemon post-success diagnostics are specifically excluded because they are not the duplicated gate-selection contract: Java success reporting uses ordinary Java diagnostics even for the Maven ownership operation, external success reports no response diagnostics there, and bounding/cleanup order is daemon-owned. Reusing the selected provider would add calls and change behavior.

=== Classification and Identity

Workspace Snapshot Composition is a stateless application/infrastructure service and composition policy inside the Core Patch and Model Engine. It is not a domain aggregate, aggregate root, entity, repository, persistence adapter, event store, durable projection, refresh service, or index. It has no stable identity or retained lifecycle. One invocation sequentially reads provider evidence and returns one immutable `ProjectSnapshot`; `ProjectSnapshot.hash`, not the composer, is the resulting evidence/staleness identity. With identical provider evidence the output is deterministic; sequential provider reads are not one atomic filesystem transaction.

The service receives its current scanner and attacher collaborators per invocation through language-neutral core ports/callbacks. Core must not import Java, Tree-sitter, TypeScript, Kotlin, daemon, or MCP types. The exact script-extension map remains one adapter-owned configuration supplied through concrete daemon/MCP wiring rather than becoming a core language table. `refactorkit-jvm` remains shared JVM semantic composition, and no new adapter-orchestration module is introduced.

=== Ordered Composition Policy

The implemented service preserves this indivisible public pipeline rather than exposing separately reorderable public merge/attach services:

. Invoke the current primary scanner. Its complete snapshot is the authoritative base.
. Invoke the secondary source-inventory collaborator with exactly `ts -> typescript`, `tsx -> typescript`, `js -> javascript`, and `jsx -> javascript`.
. If that contribution has no files, pass the exact base snapshot to the optional Kotlin stage. Do not reorder files, union the four script extensions, union ignore sets, or invoke TypeScript. With no Kotlin collaborator, return the same base instance and hash.
. Otherwise concatenate base then script files, key by `path.normalize()`, retain the later script `SourceFile` on collision, and sort surviving values by `path.toString()`. Overlay only `files`, `sourceExtensions`, and `ignoredDirectories`; union all four configured extensions and both ignore sets. Base workspace, modules, classpath evidence, auxiliary files, and pre-existing build-model authority remain intact through the overlay; only the ordered attachers may subsequently replace their own provider model.
. Invoke the supplied TypeScript attacher exactly once. Its existing same-provider replacement and provider-ID sorting semantics remain unchanged.
. Invoke the optional current Kotlin/JVM attacher last. Its existing same-provider replacement remains unchanged, and its projection continues to bind the pre-Kotlin snapshot hash.

No UUID, clock, or composer identity enters the result. Scanner and attacher exceptions propagate with unchanged identity; the composer does not catch, wrap, reinterpret, or render them, and no stage after the failing collaborator is invoked. Typed TypeScript/Kotlin unavailability remains ordinary build-model evidence rather than a composer failure.

=== Ownership, Side Effects, and Exclusions

Composition is read-only: it owns no workspace write, build/lifecycle execution, process start/stop, lock, transaction, WAL, recovery, or rollback. Daemon and MCP alone adopt this bounded extraction. Their exact retained policy boundaries are:

* refresh and saved state: invocation timing, stored root and snapshot, watcher dirty or overflow state, refresh count, and response selection;
* workspace index: open, reconcile, contribution, generation, and symbol discovery;
* pending and authority state: pending plans, lexical-review audit, admission, removal, clearing, and semantic leases;
* semantic lifecycle: toolchain or adapter discovery, start, stop, restart, reset, close, and post-apply scan-before-cleanup ordering;
* `PatchEngine` authority: preview routing, diagnostics gates, authorization, lock, WAL, apply, validation, recovery, and automatic or explicit rollback; and
* protocol policy: capabilities, JSON or text rendering, error mapping, changed-file projection, and success or refusal responses.

CLI and LSP retain their existing scan and lifecycle behavior. Recipes, testkit/direct-library behavior, a generalized scanner registry, concrete adapter imports in core, and a new orchestration module remain outside this slice. Composition returns only an immutable snapshot and owns no stored state, index, protocol, persistence, or mutation authority.

There is no persistence classification to add: the output is an in-memory immutable value. Existing transaction log/WAL state remains `TransactionLog`/`PatchEngine` responsibility. Delegated ADR review found this policy already fits ADRs 0004, 0009, and 0010 without changing ADRs 0002 or 0006; delegated C4 review validated the unchanged DSL. Reassess only if the boundary gains state, concurrency control, persistence, build/network/credential execution, concrete core-adapter dependencies, another surface, a new module, protocol behavior, writes, or different topology/relationships.

. Parse the supplied raw ID through `TransactionId.parseOrNull` exactly. Do not trim, case-fold, canonicalize, or treat the string as authority.
. Call `TransactionLog.loadRecord(parsedId)` exactly once before the engine lock, against the same normalized workspace journal used by `PatchEngine`.
. Apply the caller-selected `RollbackLookupVisibility`. If no record is visible, return not-found without guard or engine work.
. Invoke a generic surface-owned read-only guard with the exact resolved record. If it rejects, return its opaque rejection with that record before the workspace lock.
. Invoke `PatchEngine.rollback(resolvedRecord.transaction, suppliedMode)` exactly once.
. Wrap the exact engine result with the same resolved-record value. Do not reload or reconstruct the record for outcome or response projection.

`PatchEngine` intentionally reloads journal state after acquiring its own workspace lock. The executor's record is therefore the *resolved pre-lock record*: complete lookup evidence, but never a claim about current or post-rollback state. It may still report `APPLIED` after the engine has durably advanced the journal to `ROLLED_BACK`. The exact value includes operation, `forwardEdit`, transaction/rollback edit, pre/post images, created directories, snapshot hashes, lifecycle state/history, timestamps, and failure detail. Retaining it allows daemon inverse `changedFiles` projection from the pre-call `forwardEdit` without a second race-producing lookup.

=== Rollback Lookup Visibility

[cols="1,2,2,3",options="header"]
|===
|Value |Record is initially visible when |Caller |Compatibility effect

|`APPLIED_ONLY`
|`record.state == APPLIED`
|CLI, LSP, MCP
|Every non-`APPLIED` record remains observationally equivalent to absence at initial lookup. The guard and engine are not called.

|`JOURNAL_RECORD`
|Any complete decodable record whose embedded ID matches the requested ID
|Daemon
|Non-`APPLIED` records reach `PatchEngine`, which retains authority to recover or refuse, commonly with `transaction.notApplied` or `transaction.recoveryRequired`.
|===

Both values use the same single `loadRecord` plus a visibility predicate. Calling APPLIED-only `load` and then `loadRecord` would introduce a second pre-lock race and violate exact-record retention.

=== Typed Outcomes and Journal Failure Fidelity

The implemented outcome algebra is:

* `InvalidTransactionId(rawId)` — no parsed ID, journal access, record, guard, lock, or engine call;
* `TransactionNotFound(parsedId, visibility)` — no visible record, including a hidden non-`APPLIED` record under `APPLIED_ONLY`;
* `JournalLookupFailed(parsedId, failure)` — lookup threw `TransactionLogException`; no record was resolved;
* `PreflightRejected<R>(resolvedRecord, surfaceRejection)` — exact record plus unchanged opaque surface rejection;
* `RollbackCallJournalFailed(resolvedRecord, failure)` — a `TransactionLogException` escaped the one engine call after resolution;
* `RolledBack(resolvedRecord, appliedTransaction)` — exact record plus the unmodified `ApplyResult.Applied` transaction; and
* `Refused(resolvedRecord, diagnostics)` — exact record plus a detached, unmodifiable snapshot preserving the `ApplyResult.Refused` diagnostic order and values without preserving mutable list identity.

Every branch after successful resolution carries the same full record returned by the single outer lookup. Lookup-time and rollback-call journal failures are different variants rather than a nullable record. Exact `TransactionLogException` identity, code, message, and cause are retained: unsafe paths, corruption/quarantine, permission, durability, missing-record update, and I/O failures must not collapse into not-found or an ordinary engine refusal. `Refused` instead performs `Collections.unmodifiableList(ArrayList(diagnostics))`: a mutable source may change after `execute`, but the outcome retains the construction-time ordered values and rejects mutation through its public list. If the record disappears after outer resolution and the engine returns `transaction.journalMissing`, that remains an engine `Refused` with the resolved record. Only `TransactionLogException` is classified as a journal failure; a guard exception or arbitrary engine exception is not renamed.

=== Surface-owned Preflight Guard

The guard is generic over a surface rejection payload and returns allow or reject. Core neither interprets that payload nor turns the guard into authorization. CLI, daemon, and MCP use allow-all. LSP preserves its existing `requireManagedWriteSafe` order from `resolvedRecord.transaction.rollbackEdit.affectedFiles()`:

. reject if any open document is dirty relative to disk, even when unaffected;
. otherwise reject if any affected path is open, even when content matches disk; and
. preserve `DOCUMENT_VERSION_MISMATCH` and current message/rendering at the LSP surface.

The guard runs after visibility so hidden/nonexistent records cannot trigger document-state disclosure, and before `PatchEngine` acquires its workspace lock. It is intentionally not concurrency-proof and does not replace under-lock engine validation.

=== Explicit Exclusions

The executor owns no protocol/JSON/MCP/LSP/CLI rendering, error-code or exit-code projection, `RollbackMode` selection, workspace/project/snapshot refresh, symbol-index refresh, semantic-session closure, diagnostics execution/publication/rendering, pending-plan removal/clear, lexical-review audit clearing, authorization or actor invention, direct filesystem write, WAL replacement, recovery API substitution, journal schema/lifecycle redesign, response changed-file calculation, or rollback algorithm/state/image/conflict/force/metadata rule. Those responsibilities stay with the existing surfaces, `TransactionLog`, or `PatchEngine`.

This boundary changes no actor, external system, deployable container, durable store, or C4 relationship. It is an internal C3-scale realization of accepted ADRs 0002 and 0004. Delegated late reviews found no implementation contradiction in ADRs 0002/0004/0006 or `docs/c4/workspace.dsl`; no ADR or C4 update is justified. Reassess that conclusion only if future work crosses an exclusion above. Focused evidence validates the executor contract in process, while CLI/daemon/LSP/MCP adoption is source-inspected only; `PatchEngine` remains the authoritative under-lock rollback owner.

== Pending-plan Retention and Surface-owned Lifecycle

A pending plan is session orchestration state: membership of one exact retained `PatchPlan` payload under its opaque ID. It is not a new `PatchStatus`, durable record, or regenerated preview. The implemented extraction replaces only the three daemon/LSP/MCP `LinkedHashMap` implementations with one core primitive having these invariants:

The store neither observes snapshots nor decides when a plan becomes stale. == Integration Transaction Boundaries

CLI `--apply`, daemon `refactor.apply`, MCP `apply_refactoring`, and custom LSP `refactorkit.applyPlan` use the managed WAL-backed flow only after a result has been admitted as a managed plan. That general client-managed classification does not authorize lexical fallback. `refactorkit.moveClass` now calls `JavaMoveClassOperationDispatcher`; its `LexicalReview` branch returns the canonical envelope before `planToLspWorkspaceEdit`, pending-plan insertion, and both managed/client-managed rendering. == Protocol Capability Discovery

The stdio JSON-RPC daemon exposes read-only `server.capabilities` before `project.open`. `project.open` itself performs read-only recovery inspection and scan; it does not create `.refactorkit` or `workspace.lock`. Explicit `patch.recover` is separately advertised with `writesWorkspace=true`. Its response identifies the implementation and API version, fixes protocol and transport to `json-rpc-2.0` over `stdio`, and describes each documented method by stability, project prerequisite, and workspace-write behavior. Method-specific feature maps avoid version-text inference: experimental `java.importExternalClass` explicitly advertises directory targeting, preview, plan-ID apply, and transaction-ID rollback. Directory targets are canonicalized and resolved through unambiguous Java module/source-root ownership before source processing; no daemon path heuristic or direct write is permitted. The documented daemon baseline remains `beta-contract` until the planned API `1.0` inventory, migration policy, schemas, snapshots, and compatibility tests pass.

The response advertises the cross-cutting safety properties `previewBeforeApply`, `snapshotValidation`, `transactionRollback`, and `workspaceScopedWrites`. Pending source-bearing plans are LRU-bounded and cleared by project switch, discard, apply/rollback, and EOF.
