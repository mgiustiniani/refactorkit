== Patch Safety

All mutating operations are represented as `PatchPlan`s containing operation name, status, snapshot hash, confidence, required approval flag, summary, affected files, `WorkspaceEdit`, diagnostics, warnings, and risk level.

`PatchEngine` validates that:

* only preview plans can be applied;
* current snapshot hash matches the preview hash;
* edit paths stay inside the workspace root, retaining the `path.outsideWorkspace` diagnostic;
* every symbolic-link path component below the workspace root is refused with `path.symbolicLink`, conservatively even when the link resolves inside the workspace;
* text edits do not overlap; and
* ordered create, modify, rename, and delete operations have valid file existence/type transitions.

The ordered state simulation runs before the first write. It prevents a predictable later missing-file or existing-file refusal from leaving an earlier edit applied, while still allowing valid sequences such as modify then rename. Tests cover an outside-pointing symlink with no write, create followed by a missing-file delete with no partial create, and a successful modify-then-rename sequence.

Status: implementation-informed for structural/overlap validation, conservative symlink refusal, ordered state simulation, and snapshot-aware managed-write isolation. Eligible managed paths hold a non-blocking OS workspace lock across validation/apply/rollback and revalidate initially affected paths under that lock for first-party managed integrations; immutable ineligible evidence can refuse before lock acquisition. The hash-only overload is removed, all callers use the snapshot-aware contract, and snapshot hashes bind declared source scope that the engine independently walks/rehashes under lock. Classpath evidence covers active entries, prospective compiled outputs, local JAR directories, and generated declarations; all are recomputed before journaling (`TX-005` and source/classpath-scope `TX-014` closed). Modify entries are normalized into one original-content coordinate space per path/structural segment, with merged overlap checks, complete preflight rendering, and line/character-within-line validation (`TX-009`, `TX-010` closed). Full post-images are rendered before mutation, staged in same-directory temporary files, forced, atomically replaced, and followed by directory force; unsupported durability capability is reported/refused (`TX-001`, `TX-006` implementation-closed on supported filesystems). Managed flows provide filesystem-qualified WAL recovery with per-path atomic commits; they do not claim an impossible filesystem-wide atomic rename across independent paths. No RefactorKit-managed production write may bypass `PatchEngine`; native LSP client writes are outside this boundary.

== Compensation, Journal, and Recovery

Before every managed write, `PatchEngine` durably creates a versioned `PREPARED` journal record containing transaction identity, operation, forward/compensation edits, and affected-path pre/post images, then advances to `APPLYING`. Apply, rollback, and explicit restart recovery retain lifecycle states through `APPLIED`, `ROLLING_BACK`, `ROLLED_BACK`, or `RECOVERY_REQUIRED`; integrations no longer persist metadata after mutation (`TX-002` closed, `TX-001` narrowed). Read-only daemon/MCP/LSP startup calls `inspectRecovery`, which performs no lock-file, directory, quarantine or journal write and refuses incomplete state until `patch.recover` is explicitly authorized.

Transaction identifiers now enforce the generated UUIDv4 grammar; normalized transaction-log paths are contained, reject symbolic links and non-regular records, apply owner-only permissions where supported, and report coded corruption/path failures (`TX-003` closed after the audit baseline). Records now retain a versioned lifecycle, forward/compensation edits, pre/post images, failure detail, and atomically/durably replaced history. Schema-v2 canonical SHA-256 checksums, v1-on-update migration, and blocking owner-only corruption quarantine are implemented; schema-v3 adds checksummed implementation/API versions, pre/post scope hashes, and append-only validation/lifecycle/recovery events; v2 checksum verification remains backward compatible; schema-v8 adds independently verified per-image content hashes; TX-011/TX-012 are closed for the reported durability contract. Schema-v8 compensation restores text, POSIX permissions, timestamps, owner/group identity, user-defined attributes, and exposed platform ACLs and removes transaction-created parents deepest-first; external directory contents trigger conflict refusal. The v1 text contract is strict UTF-8 with exact BOM preservation and malformed-input refusal before WAL creation. Standalone directory operations are outside the stable v1 contract (`TX-013` closed by precise scope narrowing).

Normal rollback verifies exact retained post-images under the workspace lock and refuses conflicts without writes; explicit force restores pre-images and records the override (`TX-004` closed for versioned records). Snapshot-aware apply independently rescans hash-bound source roots/extensions/ignore policy under the workspace lock, so stale library snapshots cannot omit newly appeared declared-scope sources. Java classpath artifacts and discovery manifests are likewise fingerprinted and revalidated (`TX-014` closed for source/classpath scope). Recipe steps are evaluated against one evolving immutable snapshot and reduced to one recipe-wide `PatchPlan`; apply creates one WAL transaction, while planning failure writes nothing (`TX-008` closed).

Status: implementation-informed from `docs/transactionality-audit.md`. Write-ahead lifecycle, compatible startup compensation, explicit `RECOVERY_REQUIRED`, conflict-safe rollback, durable supported-filesystem replacement, and engine-owned source/classpath scope are implemented. Versioned checksums, independent image hashes, migration, quarantine, metadata policy, deterministic faults, real kills, truncation, and cross-store evidence close the qualified transactionality requirements.

== Diagnostics Model

Diagnostics use structured severity (`INFO`, `WARNING`, `ERROR`), optional source location, optional code, evidence/category, and explicit location precision (`EXACT_RANGE`, `LINE_ONLY`, `NONE`). Java diagnostics currently include duplicate symbol detection, package/path mismatch warnings, and public type/file-name mismatch errors.

Additive API `0.2` `diagnostics.v2` provides the IDE authority envelope for TypeScript/JavaScript: caller request ID, opaque semantic lease, saved and provider snapshot hashes, saved-disk or immutable-editor-overlay authority, exact compiler/toolchain and process attestation, actual compiler limits, structured ready/refused/error state, and bounded diagnostics. Exact ranges are zero-based UTF-16; line-only/no-location variants cannot be promoted to Monaco ranges by inference. Legacy `diagnostics` remains a bare array for compatibility.

The stable target also compares diagnostics before preview, after preview simulation, after apply, and after rollback where an operation requires those gates. A configured regression beyond the approved plan causes refusal.

Status: implementation-informed for the current generic/JDT gate. It does not establish the planned full-reactor, release-aware Java/Maven authority described below. Managed Java surfaces supply JDT diagnostics to a core gate that compares current and exact staged post-image snapshots under lock before WAL, refusing new errors or unavailable diagnostics. TypeScript managed gates and IDE diagnostics use the independent `typescript-compiler-exact-v1` path rather than LSP publications. Experimental Kotlin diagnostics use `kotlin-compiler-diagnostics-k2-v1`, an external K2 process over an immutable overlay with snapshot/build/toolchain attestation; compiler XML lacks trustworthy end offsets, so diagnostic locations remain explicitly line-only. The separate `kotlin-compiler-jvm-declarations-k2-v1` read row accepts exact compiler PSI declared-type selections only after successful compilation and matching JVM class-file evidence, producing type IDs from binary identity rather than offsets; an implicit companion selects its `object` keyword because it has no source name identifier. The first function row additionally binds an opaque callable ID to generated JVM owner, method name and descriptor and refuses ambiguous overload/bridge evidence. Neither read backend has mutation authority. Direct library apply requires an explicit gate (`TX-015` closed).

== Java/Maven Diagnostics Authority

Status: confirmed architecture; active, product-critical. ADR 0012 and `RPK-JAVA-DIAG-001..007` are normative. Release 8/current-release packaged diagnostics and post-model module filtering are first implemented rows; this section does not claim epic completion.

For managed Java operations, RefactorKit is the definitive semantic diagnostics and refactoring authority. Maven compile/test is supplementary acceptance evidence and never repairs, suppresses, or excuses a false RefactorKit diagnostic. RefactorKit must either analyze a complete, attested source-set semantic environment or return a concise typed unavailability/unsupported root; a partial model grants no mutation authority.

The semantic authority unit is the declared Maven reactor, effective module/variant, source set, Java platform, provider, and workspace snapshot. The declared full reactor root remains the workspace boundary. A module target is an output filter applied after full model, dependency-closure, and dependent-impact construction. RefactorKit neither reopens a child directory as a new authority nor searches ancestors/siblings outside the declared workspace.

Main and test environments remain independent. They carry effective source and safely materialized generated roots, outputs, Maven-scoped reactor/external visibility, Java settings, exact platform identity, and source-set availability. Effective dependency-scope derivation preserves declaration provenance: an explicitly declared transitive `test` scope is retained, while a dependency-management scope default supplies a value only when the declaration omits scope. Bounded REQ-JAVA-MAVEN-MOVE-AUTH-009 implements and validates that rule for six fixture-owned transitive children against matching omitted/default-`compile` and explicit-`compile` managed entries.

External Maven traversal is descriptor-closed for each source-set projection and dependency path. Every active reactor POM remains required. Every selected external node requires a complete effective descriptor closure, and every outgoing declaration from an active reactor or selected external POM has a hash-bound selected or exact derived-scope/optional/exclusion-pruned result. A deterministically pruned edge contributes no child node or descendants and therefore requires no child POM/JAR on that path; another selected path or projection restores those requirements. When child facts cannot affect selection, classification occurs before child version/range, repository, POM, effective-model, and JAR lookup. Type/classifier remain management and variant identity rather than prune reasons; ambiguity and missing descriptors on selected edges fail closed. Missing inputs propagate only through required source-set closures. Default output preserves genuine syntax diagnostics and suppresses only derivative binding/type cascades causally attributable to a typed unavailable input; verbose output may expose derivative provider rows.

Effective Maven `--release R` for Java 8 through Java 25 requires immutable, licensed, integrity-verified, hash-attested, SBOM-covered Java SE platform signatures for exactly `R`. Source grammar/compliance and compiler release flags are necessary but insufficient. The host JDK and reduced jlink runtime are never silent substitutes. A source-only/no-release configuration must identify an independently qualified JDK platform or make the affected source set unavailable.

Generated source is visible only when safely declared and already materialized. Discovery does not implicitly execute Maven, wrappers, lifecycle goals, plugins, annotation processors, credential helpers/settings credentials, or other project code. Offline/no-network remains the default under ADRs 0010 and 0011. Unnamed/classpath Maven reactors are the first qualification slice; named JPMS/module-path reactors return typed unsupported/unavailable until a dedicated complete slice proves module identity, readability, exports, and module-path semantics.

Authoritative diagnostic results bind the exact workspace snapshot, overlay/disk mode, Build Model/classpath evidence, source-set and impact closure, Java release/platform signatures, and provider identity/configuration. Default mutation policy rejects introduced or changed errors; strict mode additionally requires zero staged errors. Global source-set authority still blocks on any unavailable affected environment, including baseline unavailability. ADR 0012 defines one narrower, operation-specific Maven `moveClass` mode described below; it never removes the typed `OFFLINE_MISSING` state or claims global authority. Provider failure, evidence drift, or truncation that may hide blockers fails closed. Post-apply and rollback diagnostics attest the committed and restored snapshots respectively.

=== Immutable Review-only Guidance

Status: implementation-informed for bounded REQ-JAVA-MAVEN-MOVE-AUTH-003. ----
JavaMoveClassOperationOutcome

The `Plan` arm preserves the existing preview/refusal `PatchPlan` path. It is never inserted into a pending-plan store. Restored authority can produce only a fresh result from a full reactor rescan and new preview. This bounded Java/CLI implementation is not a generic core, library, daemon, LSP, MCP, recipe, or cross-surface result algebra.

Each guidance value uses schema version 1 and binds the exact operation/request, workspace snapshot SHA-256, and canonical evidence SHA-256. Canonical evidence is deterministic over sorted blocker facts, candidate records, omissions, restoration actions, checklist content, and expected/observed fingerprints; it contains no UUID, wall-clock timestamp, or age comparison. Every result carries at least one typed blocker with separate mandatory Maven module and source-set identity. The implemented stable codes for this bounded schema are:

* `java.maven.moveClass.sourceInventory.missingEntry`;
* `java.maven.moveClass.classpathFingerprint.mismatch`;
* `java.maven.moveClass.targetUse.recoveredBinding`; and
* `java.maven.moveClass.materializedGeneratedRootInventory.fingerprintMismatch`.

Guidance keeps exact, non-recovered `BOUND_TARGET` and `BOUND_OTHER` facts separate from `UNRESOLVED` Java lexical candidates, `JAVA_NON_CODE_RESIDUAL` occurrences, and `NON_JAVA_RESIDUAL` text paths. A recovered binding is `UNRESOLVED`, never a bound fact. Every occurrence binds the snapshot, normalized path, exact range, and content hash and reports `managedEdit=false`; lexical records are candidates or residuals, never references, edit sites, or replacement instructions. Candidate-list completeness is `COMPLETE` for three cases and `COMPLETE_WITH_TYPED_OMISSIONS` for the omitted-source case, whose one bounded omission has kind `SOURCE_INVENTORY_ENTRY`. Broader stale/truncated/unreadable omission kinds are not claimed by this slice.

Authority-restoration actions are ordered and typed: restore the source inventory, refresh classpath evidence, re-establish exact bindings, or externally restore/rematerialize a generated root as applicable, followed in every case by a full reactor rescan and a new preview. They do not execute Maven, a wrapper, lifecycle goal, plugin, annotation processor, generator, credential helper, or network request. Checklist version 1 is human/VCS-owned: create a checkpoint, inspect every candidate and omission, either restore authority or perform only confirmed manual changes, review Java non-code and non-Java residuals, run appropriate supplemental builds/tests, inspect the final diff, and use VCS for recovery. A successful manual edit or Maven build never retroactively makes the guidance binding-clean.

== Risk Model

Refactorings classify risk as `LOW`, `MEDIUM`, or `HIGH`. Examples:

* low risk: simple class/member rename where references are understood;
* medium risk: move class, safe delete, limited extract method, limited change signature;
* high risk: framework-managed types or external/import/license uncertainty.

== Java Analysis and Refactoring

Eclipse JDT Core 3.44 uses JLS25 ASTs with per-module compliance from hash-bound `java.sourceLevel` settings. Maven release/source properties and Gradle toolchain/source compatibility are detected; build descriptors are fingerprinted so post-preview changes invalidate apply. Unconfigured scanned projects default to Java 8, and acceptance covers representative Java 8, 11, 17, 21, and 25 syntax. Maven/Gradle project dependencies are hash-bound; each JDT parse sees only its owning module and transitive declared dependencies, preventing unrelated sibling modules from supplying accidental bindings. Stable operation authority is inventoried in `docs/java-capabilities.md`.

This implementation-informed syntax/compliance baseline is not Maven `--release` API authority. Compliance alone cannot select the exact historical Java SE type/member/module surface, and a running reduced jlink image can omit APIs that belong to the requested release. The active product-critical authority target is ADR 0012 and `RPK-JAVA-DIAG-001..007`; first release-platform rows are implemented, but no complete release-aware Java/Maven diagnostics implementation is claimed here.

Generated Java remains available for analysis but a shared path/annotation/header policy prevents stable rename, move, member rename, safe-delete, extract-method, change-signature, and organize-imports planners from rewriting it.

The Java adapter combines lexical/source-level scanning with selected Eclipse JDT-backed semantic-analysis slices. The following paragraphs describe recorded `v0.3.0` prototype evidence, not automatic stable classification. Core and JDT semantic symbol kinds include `ANNOTATION`; lexical top-level indexing recognizes `@interface`, while JDT visits `AnnotationTypeDeclaration` nodes and records binding identity, declaration ranges, nesting ownership, and binding-matched usage references. Annotation types participate in read-only lookup and reuse the existing class-style rename, move, safe-delete, recipe, and type-owner validation paths.

JDT also visits `AnnotationTypeMemberDeclaration` nodes and emits annotation elements as `METHOD` symbols with zero-parameter signed identities such as `com.acme.Route#path()`. Method-binding evidence supports read-only symbol/reference queries and, when analysis is clean, the existing signed `renameMember` path updates the exact declaration and binding-matched named usages such as `@Route(path=...)`. Declaration names are excluded from reference results. Implicit single-element values have no name to edit; annotation-element change-signature and default-value editing are not supported.

Signed `renameMember` uses JDT binding keys to rename transitive source-visible class/interface override families, including their scanned declarations and binding-matched call sites. Static and private methods do not form override relations, and a family containing an external declaration is refused.

For an unambiguous `FIELD` selector such as `com.acme.Stats#count`, `JavaRenameMemberPlanner` uses the exact field binding when global JDT evidence is clean and emits edits from its declaration and binding-matched reference ranges. This distinguishes qualified field access from shadowing locals and unrelated same-named fields owned by other types. If the owner already declares the requested target field, collision validation refuses the operation before semantic fallback; unclean or unresolved evidence therefore cannot bypass that safety check and instead retains the explicit lexical member fallback only when no collision exists. This field-specific behavior does not extend semantic guarantees to arbitrary unsigned method selectors.

Class rename resolves the exact target type binding when JDT analysis is clean. It generates source-range edits for the type declaration, constructor declarations, and binding-matched imports, type references, and constructor calls before renaming the source file. Binding identity leaves same-simple-name types in other packages unchanged. An unchanged requested name or an existing target symbol/file is refused. JDT parse/classpath warnings or an unavailable exact target binding trigger lexical behavior with an explicit fallback warning; reflection, framework, and generated-code warnings remain.

The recorded move-class prototype resolves the exact target type binding when JDT analysis is clean and uses binding-matched references to select files, but package/import/FQN substitutions inside those files remain lexical outside separately qualified authority. It prevents several unrelated-old-package and same-simple-name errors, keeps the package-declaration edit and source-file move in the patch plan, removes a now-redundant target-package import, avoids overlapping direct-import/FQN edits, and refuses invalid packages or existing target FQNs/files. REQ-JAVA-MAVEN-MOVE-AUTH-001 qualifies the bounded complete-`AVAILABLE` positive preview/apply/rollback row. REQ-JAVA-MAVEN-MOVE-AUTH-002 qualifies exact direct/transitive/test-only binding observer selection, exact JDT-only candidate totals, separate non-managed residual reporting, unchanged exclusions, one exact apply, and exact rollback for its isolated fixture request. REQ-JAVA-MAVEN-MOVE-AUTH-003 qualifies the four bounded plan-free guidance defects and source-built CLI JSON/refusal path; it deliberately preserves broad syntax failure as REQ-005 `LEXICAL_FALLBACK`. For the same availability mode, `006` proves that warnings outside the owner/reverse-observer closure do not demote authority while an owner/observer warning yields review-only `LEXICAL_FALLBACK`. Requirements `007`, `009`, `010`, `011`, and `012` retain their independently bounded synthetic-missing, explicit-scope, selector-pruning, ordinary-missing, and selected-descriptor evidence. `PatchEngine` rejects immutable lexical evidence before workspace-lock acquisition, while the guidance CLI branch refuses before entering `PatchEngine`. These fixture rows do not establish general support, cross-surface parity `004`, or absent broad uncertainty matrix `008`. The exact Magrathea request remains separately CLI-qualified only on Linux/JDK 21 after `010`; integration/native-matrix qualification remains open.

Safe delete uses exact JDT type-binding references when semantic analysis is clean and the exact target binding is available. Binding identity distinguishes types that share a simple name across packages. JDT parse/classpath warnings or an unavailable exact target binding trigger the existing lexical scan and an explicit fallback warning. Forced-delete behavior and framework warnings remain unchanged.

For organize imports, the semantic analyzer exposes resolved binding uses from imports and ordinary code and marks import context. Parameterized type, generic method, and variable binding keys are normalized to declaration bindings so generic uses match imported declarations. With clean evidence for a file, the planner removes an exact import only when that binding has no non-import use. Wildcard imports remain conservative. When a file is unresolved, the planner explicitly retains lexical sorting, deduplication, and same-package removal rather than claiming unused-import evidence. Preview, apply, and rollback continue through the common patch safety model.

Other conservative planners refuse ambiguous cases instead of guessing, especially extract method and structural change-signature operations. Known limitations include no annotation-element change-signature or default-value editing, incomplete compiler-backed coverage outside supported signed-method and unambiguous-field member rename (including exact annotation-element rename), type-level rename, move-class, safe-delete, annotation-type/element indexing and reference, and organize-imports slices, and limited handling of reflection, generated code, external configuration, framework strings, annotation-processor output, and unknown external callers.

For stable promotion, the JDT dependency and per-project source compliance must support representative Java 8, 11, 17, 21, and 25 source evidence while RefactorKit's documented Java 8-compatible bytecode constraint remains separate. Source roots, module relationships, JDK types, outputs, local JARs, and explicit/generated dependency classpaths must be deterministic and visible. Any semantic operation without its complete operation-specific exact evidence must refuse unless a separately classified non-semantic behavior is proven incapable of an incorrect edit; previews must label JDT-backed, lexical, and refused outcomes. A globally clean source set is not mandatory only for the qualified target-scoped Maven move proof above. Type move remains stricter: lexical scanning may veto completeness but cannot select an edit, `LEXICAL_FALLBACK` is always review-only, and authority loss must yield non-managed guidance or refusal rather than an applyable plan.

Status: implementation-informed prototype; stable capabilities are evidence-gated.

== Integration Transaction Boundaries

CLI `--apply`, daemon `refactor.apply`, MCP `apply_refactoring`, and custom LSP `refactorkit.applyPlan` use the managed WAL-backed flow. Native LSP rename and WorkspaceEdit commands are explicitly client-managed/no-rollback. Full-sync open-buffer overlays feed planning, open-document edits carry exact versions, unsupported versionable edits refuse, and managed LSP disk writes reject dirty or affected-open buffers (`TX-007` closed).

Explicit managed apply invocation is the approval event; missing authorization refuses before journaling, while successful transactions persist approval kind/surface/actor/time (`TX-016` closed). Daemon/LSP/MCP use a core-owned deterministic refusal mapper for snapshot, recovery, validation, lock, filesystem, unsafe-path, file-conflict, approval, and apply/journal categories (`TX-017` closed). Daemon apply/rollback refreshes stored session state, clears stale plans, and returns the new hash (`TX-018` closed).

Status: implementation-informed. LSP ownership/document versions and daemon state refresh are implemented; approval semantics and managed apply/rollback error categories are implemented; central diagnostics gates are implemented and required for direct apply.

== Protocol Capability Discovery

The stdio JSON-RPC daemon exposes read-only `server.capabilities` before `project.open`. `project.open` itself performs read-only recovery inspection and scan; it does not create `.refactorkit` or `workspace.lock`. Explicit `patch.recover` is separately advertised with `writesWorkspace=true`. Its response identifies the implementation and API version, fixes protocol and transport to `json-rpc-2.0` over `stdio`, and describes each documented method by stability, project prerequisite, and workspace-write behavior. Method-specific feature maps avoid version-text inference: experimental `java.importExternalClass` explicitly advertises directory targeting, preview, plan-ID apply, and transaction-ID rollback. Directory targets are canonicalized and resolved through unambiguous Java module/source-root ownership before source processing; no daemon path heuristic or direct write is permitted. The documented daemon baseline remains `beta-contract` until the planned API `1.0` inventory, migration policy, schemas, snapshots, and compatibility tests pass.

The response advertises the cross-cutting safety properties `previewBeforeApply`, `snapshotValidation`, `transactionRollback`, and `workspaceScopedWrites`. Import previews derive bounded rendered/structured diff and virtual diagnostics from the exact retained edit. Pending source-bearing plans are LRU-bounded and cleared by project switch, discard, apply/rollback, and EOF. These flags describe server behavior but must not be interpreted as one filesystem-wide ACID commit or protection from hostile writers mutating classpath artifacts after preflight validation; conflict-safe normal rollback applies only to versioned journal records with pre/post images. Capability discovery neither opens a project nor authorizes filesystem access. Daemon contract/snapshot tests exercise response metadata and lifecycle.

For stable API `1.0`, documented core patch, CLI, and daemon fields, methods, errors, exit categories, lifecycle behavior, and capability metadata are versioned contracts. Unknown methods/fields, invalid parameters, unsupported versions, stale plans, and rollback failures must have deterministic outcomes.

Status: implementation-informed baseline; API `1.0` freeze planned.
