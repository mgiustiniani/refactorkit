# RefactorKit v0.8.0 — C and shared Clang foundations

Status: **active release plan; bounded C implementation slices are in progress on
Linux x86-64, full C10-C17 qualification and 0.8.0 publication remain pending**.
Product decision: **V080-C-AND-V100-MULTIHOST-001**, approved 2026-09-10.
Baseline: published [0.7.0 bounded acceptance](v0.7.0-acceptance.md), API **0.2**.
This document does not change the source/build version or promote a released,
native-packaged or universal C capability.

[ARC42 requirements appendix](../arc42/appendix-requirements.adoc) owns the
integrated status. [ADR 0009](../adr/0009-supreme-multilanguage-v1-roadmap.adoc)
records the product decision; the [1.0 roadmap](v1.0.0-plan.md) owns the long-range
sequence. This satellite owns the bounded 0.8.0 delivery/acceptance catalogue.
Individual executable requirements must be admitted separately in Gherkin before
Story implementation; the planning row IDs below are not Gherkin receipts or
runtime operation identifiers.

## Approved decision

The product owner directed: "il multi host si fara alla versione 1.0.0. la 0.8.0
sara C. preocediamo con i tasks", then authorized starting the first scope task.

- **0.8.0 is C, before Python.** Deliver useful semantic operations, not just a
  parser, outline or rename wrapper. Reuse Clang infrastructure later for C++ and
  Objective-C; neither language is implicitly admitted to 0.8.0.
- **Multi-host qualification is deferred to 1.0.0.** It does not block 0.8.0 or
  the intervening 0.x releases. Other hosts remain **NOT VERIFIED**, never PASS.
- Local correctness, staged diagnostics, authorization, WAL/rollback, resource
  limits, independent acceptance and downloaded-artifact verification remain
  mandatory. The decision is not a general release-safety waiver.
- Preserve Java/Kotlin/TypeScript behavior and infrastructure. Do not integrate
  historical WIP, replace a global installation, move a published tag, or widen
  the catalogue merely to make a planning card appear complete.
- Clojure remains the last planned language integration before global 1.0
  stabilization. No target language is removed. Later version numbers are
  explicitly unassigned rather than mechanically renumbered by this decision.

These are **implementation/qualification targets, not supported runtime claims**.

Version-only probes observed these executables on the local host; they do not qualify tooling libraries, a bridge, operations or distribution. |
| Toolchain provisioning | Initially an explicitly configured external, verified toolchain. No implicit download, global install, compiler plugin or project wrapper execution. A bundled toolchain would require separate packaging/provenance evidence. |
| Project authority | Captured `compile_commands.json`, explicit argument/dialect/define/include/target context, TU ownership and source/header graph. Executable paths and command strings in the database are untrusted data, not permission to run them. |
| Build-manifest edits | First candidate: a separately advertised, bounded declarative CMake subset with literal source/header paths and target/include bindings (`add_library`, `add_executable`, `target_sources`, `target_include_directories`). Toolchain admission must confirm 22.1.8 is usable with the actual Clang tooling
bridge and required development/runtime artifacts. If it is not, record the
failure and revise this target explicitly; do not substitute a version silently
or call the version probe a semantic test. No new dependency is added by this plan.
Exact test-toolchain artifacts and any proposed dependencies require a recorded
preview before introduction.

A preview enumerates the configurations actually validated. Coverage of one TU
or configuration is not coverage of every macro branch, build variant, consumer
or target. Unknown required configurations refuse; warnings cannot substitute
for missing authority. API/ABI risk is reported, not certified away by compilation.

## Reuse and authority boundary

Use the existing adapter registry, Build Model SPI, snapshots/overlays, semantic
process manager, external-edit normalizer, diagnostics gates and `PatchEngine`.
C/Clang flags, AST identities, include graphs and build-provider rules belong to
the language adapter, not the language-neutral core. Adapters and handlers follow
`extract -> delegate -> response`; no duplicate transaction orchestrator or
production state in transport glue.

```text
captured C project/toolchain/configuration
  -> Clang/clangd semantic proposal
  -> validated normalized WorkspaceEdit
  -> snapshot-bound PatchPlan and staged diagnostics
  -> explicit approval -> PatchEngine -> WAL/apply/rollback
```

Validate source ranges, paths, overlaps, snapshots and operation-specific
semantic authority. A restart or toolchain/configuration change invalidates old
authority. Compiler proposals never write workspace files directly. Native LSP
editor edits remain explicitly client-managed where applicable; they do not gain
RefactorKit-managed WAL/rollback just because the adapter also has managed routes.

## Testing and release gates

- Use the existing BDD policy: one hash-bound Story scenario per implementation
  slice, effective-glue inventory before editing, compatible glue reuse, no
  duplicate runners/expressions, independently expected edits/images/diagnostics,
  and the normal numeric slice budgets. Do not treat setup/compilation failures
  as product-semantic RED.
- Route per implementation subject: Java domain specs use JavaSpec; Kotlin pure
  domain work requires an approved Kotlin spec framework or stops with
  `KOTLIN_SPEC_TOOL_UNAVAILABLE`. C sample source is fixture input, not permission
  to bypass subject-language routing. No handwritten JUnit substitute, silent
  dependency or replacement validator.
- Cover single/multifile C libraries/executables, shared headers, literal CMake
  bindings, multiple declared macro configurations and relevant mixed/unsupported
  consumers. Hostile input tests must prove refusal without unowned writes.
- Verify exact pre/post images, range normalization, stale preview refusal,
  no-WAL refusal where required, managed apply, rollback conflicts and recovery.
  Test process timeout/cancellation/restart and closure with real bounded peers;
  protocol liveness tests are not compiler-semantic success evidence.
- Preserve existing Java/Kotlin/TypeScript acceptance boundaries. Report actual
  pass/skip/refusal results and static findings; do not call skips passes or
  report unmeasured coverage as a number.
- Bind source revision, test results, toolchain/configuration, embedded runtime,
  archive and capability matrix before publication. Verify draft/candidate and
  public downloads independently, including checksum, SBOM and attestations.
  Compiler/toolchain distribution and licensing must be explicit; bundled Java
  does not mean bundled Clang.
- Tags/assets are immutable after publication. A later defect needs a new
  version, not a retag of a published release. Updating the local installation
  is a separate explicit operation.

## Multi-host scheduling and preserved history

At **1.0.0**, qualify every advertised host/platform on the actual stable
candidate, with native builds, toolchain, filesystem/process/transaction tests,
checksums, SBOM/provenance and downloaded-runtime execution. The reference matrix
remains Linux x86-64, Windows x86-64, macOS x86-64 and macOS arm64; any change to
that advertised stable matrix needs an explicit decision.

Until then, qualify the one platform actually shipped for each interim release;
do not cross-publish an untested host archive or label another host PASS. Existing
0.5/0.6 native evidence and the narrow 0.7 waiver remain unchanged historical
records, not receipts for 0.8 or 1.0. Neither old failed runs nor known capability
limits are retroactively promoted by this new scheduling decision.

This scope task changes documentation only. The current CI matrices/finalizers
and source/API versions remain unchanged; **C17 must implement the prospective
single-platform CI/release selection before any 0.8 CI dispatch or push**. It
must preserve local/native identity and supply-chain gates rather than disable
verifiers or relabel historical multihost results.

## Explicit exclusions and next admission

No C++ namespace/module/template or Objective-C selector/ARC work in 0.8.0. No
arbitrary build execution, automatic toolchain installation, universal macro
transformation, arbitrary GNU extensions or C23 constructs, whole-program ABI guarantee,
filesystem-wide ACID/power-loss guarantee, live replacement-race guarantee, IDE
frontend, new global framework, blanket performance claim or numerical coverage
claim is granted by this plan. Retain existing safety limits until new evidence
actually qualifies a stronger cell.

Current frontier: bounded C slices C02-C15 (toolchain, compilation database,
symbol index, diagnostics, rename, format, move, rename-prefix, change-signature,
extract, inline, safe-delete, organize-includes, relocate-component) and the
daemon/CLI/MCP/LSP surfaces are implemented on Linux x86-64 as bounded slices.
**Remaining: C16 integration completion and C17 exact-source local-platform
qualification, independent review, supply-chain/download verification and
publication.** Each further slice must admit/inspect its first Story and exact
artifacts before source changes; the version-only observation is planning input,
not GREEN, and a bounded implementation slice is never full-row acceptance.

## C17 local qualification and publication evidence requirements

implemented in `.github/workflows/ci.yml`:

- `workflow_dispatch` input `qualification_platform` (default `linux-x86_64`).

  the `maven-move-class-native` matrix is restricted to the single actually
  qualified platform (`linux-x86_64`). Other hosts remain **NOT VERIFIED** until
  their 1.0.0 qualification; they are never relabelled PASS.
- For `push`/`pull_request` the historical multihost matrix is preserved and is
  not rerun for 0.8 development.

Final C17 acceptance (waits for the completed catalogue) requires:

- BDD/golden/protocol fixtures for every advertised C capability.
- Resource/hostile-input/crash/rollback checks on managed paths.
- Java/Kotlin/TypeScript regression (existing behavior preserved).

- Other platforms remain NOT VERIFIED until 1.0.0.

The C17 CI-selection setup is implemented; the full qualification/publication
waits for the complete catalogue. No 0.8 CI dispatch, push, tag or release has
