## Findings

### HIGH — Organize-imports removes a used Java static field and changes runtime behavior

`KotlinCompilerUsageExtractor.java:343-360` records an external `FirPropertySymbol` only when it has a getter. Java static fields such as `Integer.MAX_VALUE` therefore have no usage identity. `KotlinOrganizeImportsPlanner.kt:69-105,155-198` trusts that incomplete fingerprint when classifying imports as unused.

This violates `docs/requirements/kotlin-jvm-organize-imports-callables-formatting.md:7-14`.

Executable fixture:

```kotlin
package probe
import java.lang.Integer.MAX_VALUE
import java.lang.Long.*

fun value(): String =
    "${MAX_VALUE::class.qualifiedName}:$MAX_VALUE"

fun main() { print(value()) }
```

Applying `kotlin organize-imports` returned `status: applied`, removed `Integer.MAX_VALUE`, and reported no diagnostics:

```text
before: kotlin.Int:2147483647
after:  kotlin.Long:9223372036854775807
```

This is a cleanly compiling binding substitution incorrectly reported as unused-import removal.

### HIGH — Parameter rename can exchange bindings while its fingerprint remains equal

Conflict checking only considers other parameters at `KotlinChangeSignaturePlanner.kt:122-136`. More importantly, the staged fingerprint at `KotlinChangeSignaturePlanner.kt:241-258` records usage path, target and token—but not the source range. Combined with the missing Java-field evidence above, target uses can move between locations in one file without detection.

This violates the exact non-target binding and usage requirements at `docs/requirements/kotlin-jvm-change-signature-parameter-rename.md:19-31`.

Executable fixture:

```kotlin
package probe
import java.lang.Integer.MAX_VALUE

private fun value(old: Int): Long {
    val first = run {
        val MAX_VALUE = 7
        old.toLong()
    }
    return first + MAX_VALUE
}

fun main() { print(value(5)) }
```

Renaming `old` to `MAX_VALUE` returned `status: applied` and `diagnostics: []`. The nested use rebound to the local value while the imported field use rebound to the parameter:

```text
before: 2147483652
after:  12
```

### HIGH — Extract-method does not prove that the inserted call resolves to the new helper

`KotlinExtractMethodPlanner.kt:60-62` checks collisions only against source declarations. It then inserts a textual call/helper at `:75-81`, while post-image validation at `:89-97` proves only that the target and helper declarations exist. It never proves that the replacement call binds to that helper or preserves existing callable bindings.

Executable fixture:

```kotlin
package probe
import java.util.concurrent.ForkJoinPool.getCommonPoolParallelism

fun answer(): Int = 40 + 2
fun imported(): Int = getCommonPoolParallelism()
fun main() { print("${answer()},${imported()}") }
```

Extracting line 3 under helper name `getCommonPoolParallelism` returned `status: applied` with no diagnostics. The explicit import wins over the newly declared helper:

```text
before: 42,31
after:  31,31
```

The generated private helper exists but is unused; the replacement call resolves to the imported Java method.
