## Blocking findings

### 1. Typealias-expanded type bindings are silently omitted, allowing semantic rebound in both gates

`KotlinCompilerUsageExtractor.java:524-544` and `:547-583` expands a typealias to its underlying `ClassId`, but records it only when the source token matches the underlying binary simple name or an `as`-import alias. A source spelling such as `Chosen` is therefore silently absent rather than producing incomplete evidence.

That omission is trusted by:

- `KotlinJvmMoveDeclarationPlanner.kt:255-264,357-367`
- `KotlinOrganizeImportsPlanner.kt:74-115,171-213`

Executable probes against the packaged candidate:

- `/tmp/probe-a8822-move-typealias-rebound.py`: moved a plain public function using same-package `Chosen::class`, where source `Chosen` aliased `TimeUnit` and destination `Chosen` aliased `ChronoUnit`. Result: exit `0`, `status=applied`, no diagnostics, exact consumer import updated, WAL written, behavior changed from `java.util.concurrent.TimeUnit` to `java.time.temporal.ChronoUnit`.
- `/tmp/probe-a8822-organize-typealias-rebound.py`: removed explicit `source.lib.Chosen` in the presence of `other.shadow.*`. Result: exit `0`, `status=applied`, no diagnostics, WAL written, and the same `TimeUnit` → `ChronoUnit` identity change.

This violates the exact outbound-type requirement at `kotlin-jvm-move-top-level-function-and-companion-refusal.md:15` and complete import fingerprint requirement at `kotlin-jvm-organize-imports-callables-formatting.md:7-14`. If typealiases are outside scope, they must cause typed refusal—not mutation authority.

### 2. Maven `-Xplugin` compiler-option declarations bypass plugin refusal

`MavenEffectiveReactorBuilder.kt:530-567` detects `<compilerPlugins>`, `<pluginOptions>`, plugin dependencies, and kapt/KSP goals, but ignores compiler plugins supplied through Kotlin Maven `<args>`, including `-Xplugin=...`. Consequently `JavaProjectScanner.kt:235-237` emits no plugin ID and `KotlinJvmBuildModel.kt:127-135` does not return `kotlin.compilerPluginsUnsupported`.

Using a valid local `kotlin-serialization-compiler-plugin-embeddable-2.0.21.jar` configured as:

```xml
<args>
  <arg>-Xplugin=${project.basedir}/custom-compiler-plugin.jar</arg>
</args>
```

produced:

- `/tmp/probe-a8822-maven-xplugin-move.py`: move applied, source/import changed, WAL written.
- `/tmp/probe-a8822-maven-xplugin-valid-apply.py`: bounded extract applied, helper inserted, WAL written.

Both returned no diagnostics or refusal. This contradicts the plugin-dependent move exclusion and the stable compiler-plugin refusal matrix at `kotlin-advanced-shapes-and-platform-matrices.md:29,34`.
