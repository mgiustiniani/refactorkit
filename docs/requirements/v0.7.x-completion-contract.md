# RefactorKit 0.7.x completion contract

Status: active release-blocking contract, subject to the explicit `0.7.0` exception below.

## Approved 0.7.0 exception — 2026-09-08

[Approved change V070-LOCAL-HOST-ACCEPTANCE-001](v0.7.0-local-host-acceptance-approved-change-001.md)
waives the repeated multi-host qualification gate for `0.7.0` across J1/T5/K5/I1.
Local correctness, regression, packaged acceptance and safety checks remain required.
Absent host reports are not PASS, and final-candidate platforms other than the
actually tested host must be marked not verified. This exception takes precedence
over conflicting matrix/closure clauses below and in the linked release ledgers;
it does not waive functional work or claim independent review/publication.

## Decision

The `0.7.x` band is not complete at K4. Every still-open K5, T5, J1 and I1 row
listed in `docs/releases/v0.7.0-plan.md` is release-blocking for closure of the
band. Work remains split into small requirement-first, independently previewable,
tested and qualified commits; this scope decision does not authorize one broad
rewrite or weaken refusal behavior.

API remains `0.2` throughout the band. Compatibility projections may be retired
only by an additive/versioned migration with executable compatibility evidence.

## Mandatory workstreams

### Shared JVM authority

Before broad public Kotlin or Java/Kotlin mutation, RefactorKit shall establish a
shared JVM declaration/reference identity mapping for at least one public type
and one member shape. Kotlin K2 and Java JDT evidence must map independently to
the same binary identity and exact source tokens. If either side, a generated
boundary, an external consumer or the build/classpath model is incomplete, the
operation shall return a stable typed refusal.

### Kotlin K5

Every K5 catalogue row shall have:

1. an English requirement and executable refusal/success tests;
2. compiler/Analysis API evidence rather than lexical authority;
3. normalized exact edits and staged diagnostics;
4. CLI/daemon/MCP transport where the operation is user-visible;
5. managed apply, WAL, recovery and rollback for writes;
6. native packaged qualification for each promoted mutation family.

Capability matrices may classify unsupported multiplatform, Android, plugin or
framework shapes as `REFUSED`; completion requires truthful detection and stable
reasons, not fabricated support.

A Kotlin companion object is not an independently movable declaration. Moving an
enclosing type or its whole declaration file may carry the companion unchanged.
Extracting companion members or a companion into another declaration is a
separate future operation. A standalone companion-object move request must return
a stable typed refusal. Existing source that treats a companion as a standalone
`moveDeclaration` target is prototype/negative evidence and is not a qualified
K5 row.

### TypeScript/JavaScript T5

T5 is an operation catalogue, not one catch-all “move” or “inline” capability.
The release ledger shall track these rows independently:

1. source-file relocation, including compiler-proven import/export updates;
2. declaration move between files/modules;
3. module-specifier rewrite and TypeScript project-reference migration;
4. organize-import modes (`All`, `SortAndCombine`, and `RemoveUnused`);
5. extract-function and extract-constant actions;
6. inline-variable actions;
7. change-signature; and
8. inline-function only as a separately proven row, never inferred from
   inline-variable or extract evidence.

Typed TypeScript refactor authority is toolchain-, semantic-lease-, snapshot-,
UTF-16-selection-, preference-, and returned-action-bound. The adapter must use
the pinned TypeScript compiler/server protocol through a typed anti-corruption
layer: `getEditsForFileRename`, `organizeImports`, or an exact
`getApplicableRefactors` / `getEditsForRefactor` action pair. Invented LSP method
shapes, command names that return `void` without an exact edit-capture path, source
presence, or a generic `moveSymbol`/`inlineMethod` label grant no authority.
The originally inspected advanced planner source was therefore prototype/negative
evidence until replaced or made to refuse truthfully. The bounded replacement and
public-session integration now have [local evidence](../releases/v0.7.0-t5-local-safety.md),
not independent or final-candidate acceptance; this does not relax the authority
requirements above or close a release row.

Dynamic or mixed JavaScript never inherits TypeScript completeness. A JavaScript
row may close through a truthful stable typed refusal when compiler evidence is
incomplete; that refusal is a supported safety outcome, not successful mutation.

### Surface and composition authority

API `0.2` LSP module/identifier rename remains a version-checked,
client-managed edit proposal with `refactorkitRollbackAvailable=false`. It does
not become RefactorKit-managed merely because the proposal is semantically typed.
Only the explicit retained-plan apply path through `PatchEngine` may be qualified
for WAL, recovery and rollback, and that managed path keeps the existing dirty or
affected-open-document guard.

A recipe may compose managed mutations only while retaining the exact child
operation identity, `PatchPlan`, evidence, authority lease, auxiliary inputs and
diagnostics gate required for the final candidate. It must not relabel an
authority-owning child as `recipe:<id>` and then apply it through a weaker generic
gate. Until a recipe-wide authoritative evaluator is separately proven, a recipe
may contain at most one authority-owning mutation plus non-mutating projection or
summary steps; incompatible, stale, review-only or second authority-owning steps
must refuse before WAL.

### Java/shared-platform J1

All J1 rows are included, including bounded JDT catalogue expansion and
transactional `java.moveAcrossMavenModules`. Maven reactor edits must be offline,
plugin-free, cycle-safe, comment/unknown-element preserving and committed with
Java edits in one `PatchEngine` transaction. Compatibility behavior for API
`0.2` remains covered.

### Integration and release I1

Closure requires representative Maven, Gradle, mixed and refusal fixtures;
unit/property/golden/protocol/agent/hostile/stress/timeout/crash tests; complete
native packaged mutation acceptance; support matrices and limitations; checksums,
SPDX SBOMs, provenance/attestations and independent downloaded-asset smoke.

Every release claim must join to one release evidence identity: repository,
immutable tag, full commit SHA, clean/version state, platform/architecture,
archive name and SHA-256, extracted runtime/tree identity, fixture/request/scenario
identity, toolchain hashes, operation-family report hashes, SBOM hash, and
attestation subject digest. A local package pass, source-built test, queued or
running CI job, intermediate Actions artifact, and independently downloaded
published asset are distinct evidence subjects and may not substitute for one
another.

## Sequencing

The product-owner priority from 2026-07-17 is retained. The local P0
build-scaffolding gate above is resolved by a non-capability scaffolding change
and must remain green; that evidence does not close any item below:

1. close every J1 Java catalogue and Maven ownership-migration slice;
2. close every T5 TypeScript/JavaScript slice;
3. resume and close the remaining K5 Kotlin slices;
4. close I1 global regression, native packaging and immutable release publication.

The already-qualified shared JVM boundary remains a prerequisite and the completed

require a narrowly scoped shared-kernel correction, but unrelated Kotlin feature
expansion shall not displace the ordered priority. Work remains requirement-first
and independently accepted; this ordering does not authorize broad rewrites.

## Closure gate

The band closes only when every required K5, T5, J1 and I1 checkbox is complete
with linked acceptance evidence, subject for `0.7.0` to the explicitly waived
multi-host rows above; a waived row is not a passing qualification. All existing
Java/TypeScript/Kotlin behavior must remain green, the working tree must be clean,
and artifacts and reports must reconcile to one release evidence identity.
Each final shipped asset must be independently downloaded and integrity-verified,
and the final immutable `v0.7.x` tag must be published. Until then the version remains a
snapshot and no roadmap text may describe the complete `0.7.x` band as released.
