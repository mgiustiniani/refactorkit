= ADR 0002: Use PatchPlan and PatchEngine Preview-Apply-Rollback Safety Model
:toc:
:sectnums:

Date: 2026-07-10

Status: Accepted; qualified transactionality implementation and evidence complete

== Context

RefactorKit exists to replace fragile text edits with deterministic, reviewable refactoring operations. Code changes may rename, move, create, delete, or modify files, so direct writes would make failures difficult to inspect and recover from.

All integration surfaces need one explicit safety model. For `apiVersion=1.0`, that model is a versioned product contract rather than an implementation convention.

== Decision

Represent each planned change as a `PatchPlan` containing a workspace edit, affected files, diagnostics, warnings, confidence, evidence classification, and snapshot information. Apply changes through `PatchEngine` only after preview, validation, and user or caller approval. Record transaction metadata sufficient to diagnose an interrupted apply and to roll back every managed write.

At `apiVersion=1.0`, edit ordering, stale-snapshot rejection, overlap rejection, workspace and symlink boundaries, atomicity by filesystem capability, partial-failure reporting, transaction-log handling, apply, and rollback behavior are normative versioned contracts. Production workspace writes must not bypass `PatchEngine`.

Before the first write, `PatchEngine` validates structural paths and overlapping edits, then simulates the ordered create, modify, rename, and delete operations. The simulation tracks file existence and type transitions so that a predictable later refusal caused by a missing or existing file does not occur after earlier edits have already been applied.

Every symbolic-link path component below the workspace root is rejected with diagnostic code `path.symbolicLink`, including links that resolve to a location inside the workspace. This conservative rule complements the existing `path.outsideWorkspace` rejection.

Where an operation contract requires diagnostics, compare diagnostics before preview, after preview simulation, after apply, and after rollback. Validation regression beyond the approved plan causes refusal rather than an unreported or best-effort write.

This decision records the intended stable safety model. It does not assert that the current implementation satisfies that model. At the audited baseline, server-managed and CLI apply flows are previewable, preflighted, compensatable batches: they write sequentially and return compensation only after a completely successful apply. They are not ACID transactions and are not crash-safe or durably atomic.

== Consequences

* CLI, daemon, LSP, and MCP clients can present shared preview semantics, but each integration must accurately classify who owns the write and recovery record.
* The engine can reject a supplied stale snapshot hash, overlapping edits within one modify operation, and unsafe workspace or symbolic-link paths before writing.
* Compensation metadata gives callers a recovery path only after a completely successful managed apply in the tested no-concurrency, no-interruption case; it is not evidence of crash recovery.
* Refactoring implementations must produce structured edits instead of mutating files directly.
* Complex operations may need additional diagnostics before they can be safely accepted.
* Stable acceptance requires property, stress, corruption, interruption, unsafe-path, concurrency, and hash-restoration evidence; the accepted architecture does not by itself prove those behaviors complete.
* Preflight validation reduces predictable partial writes but does not provide filesystem atomicity, isolation, durability, or all-or-nothing behavior after I/O or process failure.
* The stable contract must define atomicity, consistency validation, isolation, durability, compensation, rollback, crash recovery, transaction boundaries, failure models, approval, and degraded filesystem guarantees separately.
* Closure requires a versioned write-ahead journal and lifecycle, safe staging and replacement according to filesystem capability, one-writer locking, affected-file preconditions, conflict-safe rollback, complete edit rendering, stable error categories, diagnostics gates, and recovery reporting. These are required consequences of this decision, not completed work.

== Evidence

The late first v1 S1 `PatchEngine` hardening slice includes test evidence for:

* rejecting a symbolic link to a location outside the workspace without writing;
* rejecting a create followed by a delete of a missing file without leaving the earlier create applied; and
* accepting a valid modify-then-rename sequence through ordered state simulation.

The link:../transactionality-audit.md[transactionality audit] at commit `5f47ad0` limits that evidence to predictable preflight failures and successful compensation in controlled cases. It does not prove durable atomic transactions.

== Audited Limitations

The following open findings qualify the accepted direction and must not be read as implemented fixes:

* `TX-001` is implementation-closed on supported filesystems: apply renders and stages complete post-images before mutation, catches failure, performs compatible compensation, and durably reports `RECOVERY_REQUIRED`; destructive fault evidence remains a release gate.
* `TX-002` is closed: `PatchEngine` durably persists and advances the versioned write-ahead lifecycle before and through workspace mutation; integrations no longer save metadata afterward.
* `TX-003` is closed after the audited baseline: transaction IDs enforce the generated UUIDv4 grammar; normalized contained log paths reject symbolic links and non-regular records; owner-only permissions are applied where supported; and malformed records produce coded failures. Durable journal lifecycle/integrity work remains under `TX-002`, `TX-011`, and `TX-012`.
* `TX-004` is closed for versioned journal transactions: normal rollback verifies exact affected-path post-images and refuses `rollback.conflict` without writes; explicit force restores pre-images and records the destructive override; legacy records without images require manual recovery.
* `TX-005` is closed for RefactorKit-managed writes after the audited baseline: `PatchEngine` holds a non-blocking OS file lock across validation/apply/rollback, snapshot-aware apply revalidates affected paths under that lock, the hash-only overload is removed, and all first-party/test callers use the protected contract.
* `TX-006` is closed for reported supported filesystems: apply/rollback/recovery use same-directory staging, file force, required atomic replacement, delete/parent-directory force, durable directory creation, permission preservation, temp cleanup, and explicit capability refusal.
* `TX-009` is closed: modify entries are normalized per path/structural segment into one original-content coordinate space, with overlap validation across the merged set and one normalized journal edit.
* `TX-010` is closed: line and character-within-line bounds are enforced, exact line-end positions remain valid, and preflight renders complete results before journal creation or mutation.
* `TX-011` is closed: schema-v8 checksummed records include schema and implementation/API versions, operation, forward/compensation edits, pre/post images and engine-scope snapshot hashes, approval, timestamps, failure detail, and append-only validation/lifecycle/recovery history. Independent per-image content hashes and destructive boundary evidence are included.
* `TX-012` is closed for the reported durability contract: create/update/delete persistence durably flushes files/directories and lifecycle replacement requires a same-directory atomic move; versioned checksums/migration are implemented; corrupt records are atomically quarantined and block managed writes; capability reporting and deterministic/real-kill/raw-truncation/cross-store evidence qualify the guarantee.
* `TX-013` is closed for the narrowed v1 file-edit contract: schema-v8 images retain POSIX permissions, timestamps, owner/group identity, user-defined attributes, and exposed platform ACLs and apply/rollback/recovery restore them; created parent directories are conflict-checked and removed on rollback/recovery; strict UTF-8/BOM behavior is explicit; standalone directory operations are explicitly outside the stable v1 edit model.
* `TX-014` is closed for declared source and Java classpath scope: snapshot hashes bind module/source-root metadata, extensions, ignore policy, language IDs, paths, source content, and classpath evidence. Under lock the engine independently walks and rehashes sources plus active/prospective classpath entries, local JAR directories, and generated declaration files, refusing changed evidence before journaling.
* `TX-015` is closed: a core gate compares diagnostics on current and exact staged post-image snapshots under lock before WAL, refusing new errors/provider failure. All direct callers must provide `DiagnosticsGate`; ungated apply overloads were removed before API freeze.
* `TX-016` is closed: explicit managed apply invocation is the approval event; approval-required plans refuse missing authorization, and the transaction persists approval kind, surface, actor, and timestamp. Legacy records are marked `LEGACY_UNRECORDED`.

== Residual Risks and Open Scope

* At the audited `5f47ad0` baseline, most findings were open; subsequent implementation closes TX-001 through TX-018 for the qualified managed-file contract.
* Startup recovery handles compatible interrupted lifecycle states and blocks conflicts; deterministic faults, real process kills, raw truncation, corruption quarantine, compensation failure, and cross-store lifecycles are covered.
* Managed snapshot-aware writes close the normal RefactorKit-writer scan-to-mutation race and independently detect newly appeared declared-scope sources and changed Java classpath artifacts; native editor-applied LSP edits and hostile concurrent filesystem namespace replacement remain outside that evidence.
* Stable `1.0` transactionality must not be claimed until the required guarantees are either evidenced or narrowed to precise degraded guarantees.

=== Authoritative candidate evaluation

For an edit that can change hash-bound semantic metadata, the Core Patch and
Transaction Execution bounded context owns one language-neutral application
port and its invariants. For each exact immutable candidate, that port returns
exactly one transient immutable value containing one authoritative
`ProjectSnapshot` and the diagnostic multiset evaluated from that same
candidate. Core is the upstream policy owner; a language-specific bounded
context is a downstream provider through an anti-corruption layer and cannot
introduce a language type or language dependency into core.

The evaluation value is not an aggregate, entity, domain event, repository,
projection, or durable service. It has no entity identity or independent
lifecycle: its value identity is the authoritative snapshot identity together
with the exact diagnostic multiset for one invocation, and it is discarded
within the lock-held `PatchEngine.apply` attempt. Its consistency boundary is
that apply attempt and its existing transaction. Natural cardinality is one
candidate request to one value; no reactive stream, subscription, hidden
blocking boundary, mutable singleton, or God service is introduced.

Core constructs or validates the authoritative result while preserving the
candidate's normalized workspace root; exact source/auxiliary partition;
normalized tracked paths, language IDs, and bytes; `sourceExtensions`; and
`ignoredDirectories`. Only `modules`, `classpathEvidence`, and `buildModels` may
be rehydrated. Provider-owned temporary roots, a changed tracked inventory,
repartitioned files, or different tracked bytes are never snapshot authority.

The bounded implementation enforces transitive immutability. At construction,
`AuthoritativeDiagnosticsEvaluation` deep-detaches every caller-owned outer and
nested collection reachable through:

* `ProjectSnapshot`, including its files, auxiliary files, source/ignore sets,
  modules, classpath evidence, and build models;
* every `Module`, including all source-root, classpath, dependency, output, and
  language-settings collections;
* every `BuildModel`, `BuildModule`, and `BuildSourceSet`, including their nested
  module/source-set, diagnostic, attribute, source-root, classpath, output, and
  dependency collections; and
* the evaluation diagnostics list and every `DiagnosticDetails.fields` map.

No retained caller alias or attempted mutation through an exposed outer or
nested collection may change the evaluation or produce a partial change. The
complete exposed snapshot-and-diagnostic graph is the construction-time value
identity. After any such attempt, the exposed `ProjectSnapshot.hash` and a fresh
canonical hash recomputed from all exposed snapshot state must both equal its
construction-time snapshot identity; the complete diagnostic multiset,
including every details map, must remain equal to its construction-time
component of that identity.

Core, not the downstream provider, performs path acceptance on every returned
result. Against the preserved candidate workspace it resolves and
normalizes each `Module.root`; every entry in that module's `sourceRoots`,
`mainSourceRoots`, `testSourceRoots`, `generatedSourceRoots`, and
`generatedTestSourceRoots`; every `BuildModule.root` in every returned
`BuildModel`; and every source/generated-source root in each `BuildSourceSet`.
Each must remain workspace-contained. An anti-corruption-layer translation or
provider-owned isolated materialization is not authority to introduce an
arbitrary root.

An explicit absolute external classpath entry remains admissible only through
the existing explicit external-classpath policy. For the exact path and kind
bound by that policy, core independently recomputes the entry's current
no-follow path/kind fingerprint and requires exact equality with the supplied
evidence. Missing or unreadable evidence, path or kind drift, symlink
substitution, or a fabricated fingerprint is an authority violation. For a
baseline or staged result it refuses before `PREPARED` and before any WAL
record; at a committed or restored evaluation it cannot attest the image and
follows the existing rollback/recovery rules. Provider authority includes
neither arbitrary roots nor fabricated classpath facts.

`WorkspaceEditSimulator` therefore remains exact post-image snapshot authority
only when the edit cannot change hash-bound semantic metadata. For a
model-changing edit it produces the exact staged file candidate `C1`, not an
authoritative successor that may retain `S0` modules, classpath evidence, or
build models.

=== Lock, WAL, apply, and restoration invariants

The implemented bounded ordering is fail-closed:

* Baseline evaluation returns a snapshot exactly equal to `S0` and baseline
  diagnostics `D0`; a baseline mismatch or unavailable evaluation refuses the
  apply without a WAL record.
* Core simulates the normalized edit to exact candidate `C1`. Staged evaluation
  preserves the candidate shell described above and returns authoritative
  snapshot `S1` plus staged diagnostics `D1` for that exact image.
* After provider completion and before WAL creation, core repeats under the
  existing workspace lock both engine-owned workspace revalidation and the
  operation-authority lease revalidation. Drift, provider unavailability, or a
  failed diagnostic gate refuses before `PREPARED` and before workspace
  mutation.
* Rendered transaction post-images must equal the tracked image of `C1` and
  `S1`. The existing schema-v8 `PREPARED` record stores
  `preSnapshotHash=S0.hash` and `postSnapshotHash=S1.hash`; the latter is not a
  file-only successor with stale semantic metadata.
* After apply, authoritative evaluation of committed bytes must reproduce
  exactly `S1.hash` and the complete `D1` multiset under the existing diagnostic
  identity. Hash mismatch, diagnostic mismatch, or evaluation unavailability
  triggers automatic rollback through the same journaled transaction.
* After that restoration, authoritative evaluation must reproduce exactly
  `S0.hash` and `D0`. A failure to restore or attest that baseline remains an
  explicit recovery failure rather than a successful apply result.

=== Compatibility and persistence

The existing `DiagnosticsGate.enabled` and `DiagnosticsGate.disabled` call and
no-call behavior, provider invocation order, diagnostic identity, error-only
multiset regression and approved-regression semantics, and typed
unavailability/refusal behavior remain exact for diagnostics-only evaluation.
Operations whose edits cannot change hash-bound semantic metadata retain their
existing exact simulator-derived pre/post hashes. Existing journal records and
hash meanings are not rewritten.

The authoritative evaluation is invocation-scoped and transient. The existing
schema-v8 transaction journal remains the sole WAL, idempotency, and exact-result
store; the bounded implementation uses no schema bump, historical migration,
new repository or other store, event store, outbox, audit-evidence store,
immutable document store, or projection. It adds no durable evaluation
serialization and no core language dependency.
